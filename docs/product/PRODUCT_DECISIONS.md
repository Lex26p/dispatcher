# Реестр продуктовых решений «Диспетчера»

**Статус:** промежуточная фиксация принятых продуктовых решений.  
**Редакция:** 4.  
**Дата:** 7 августа 2026 года.  
**Охват:** решения от `PRD-Q001` через `PRD-Q676`, включая заменяющие решения с суффиксами `R` и `N` и уточнения первой независимой сквозной проверки.

Решения со знаком `*` приняты по рекомендованному варианту, но затем уточнены прямыми комментариями пользователя. Текст уже содержит итоговую формулировку.

Суффиксы `R` и `N` обозначают итоговые вопросы после пересмотра прежнего раунда. Отвергнутые черновые варианты этих раундов не являются решениями и в реестр не включаются.

| ID | Вариант | Принятое решение |

| `PRD-Q003` | A | Одна установка обслуживает одну организацию с множеством регионов, филиалов, площадок и объектов; обслуживание нескольких независимых организаций возможно внешним контуром управления несколькими установками. |
| `PRD-Q004` | B | Платформа выполняет верхнеуровневый мониторинг, координацию и разрешённое управление; hard-real-time, safety и иной basic deterministic control, требующий локальных гарантий, остаётся на PLC/локальных контроллерах. ## Профили Full, Compact и Edge

| ID | Вариант | Принятое решение |
|---|---:|---|
| `PRD-Q023` | B | Обязательное ядро — функциональный минимум SCADA: организация, локации, пользователи, права, оборудование, параметры, подключения, текущие данные, события, аварии, команды, аудит, жизненный цикл конфигурации, базовая веб-оболочка, администрирование, каталог, резервное копирование и диагностика. |
| `PRD-Q024` | B | Full, Compact и Edge — один продукт с общей моделью, но разными профилями установки, масштабом, допустимым составом, распределённой ролью и эксплуатационными ограничениями. |
| `PRD-Q025` | B | Compact может быть присоединён к Full и преобразован в Edge с сохранением данных и конфигурации через управляемый мастер и анализ конфликтов. |
| `PRD-Q026` | C | Эксплуатационная конфигурация Edge принадлежит Full; локально на Edge управляются только ограниченные сервисные настройки узла. |
| `PRD-Q027` | B | При потере Full Edge продолжает опубликованные локальные функции: опрос, нормализацию, историю, события, аварии, разрешённые команды, локальные правила, расписания, сценарии, ограниченный веб-интерфейс, аудит и буферизацию. |
| `PRD-Q028` | C | Локальный интерфейс Edge — ограниченная оболочка на общей дизайн-системе: состояние объектов, опубликованные страницы и мнемосхемы, аварии, локальные тренды, разрешённые команды, документы и диагностика; без глобального администрирования и Каталога. |
| `PRD-Q029` | C | Неустановленные сервисы отсутствуют в рабочем интерфейсе, но доступны для обнаружения в административном Каталоге. |
| `PRD-Q030` | C | Исполняемый пакет отделяется от использованного контента; перед удалением предлагаются сохранение закреплённой версии, замена, отделение локальной копии, архивирование проектов или осознанное удаление. |
| `PRD-Q031` | B | Платформа не зависит от постоянного Интернета: эксплуатация, лицензирование установленного экземпляра, компоненты, резервное копирование и администрирование автономны; обновления доступны через локальные репозитории и подписанные офлайн-пакеты. |
| `PRD-Q032` | C | Full управляет составом Edge через профили и группы с отображением желаемого и фактического состояния и контролируемыми отклонениями отдельных узлов. |

| `PRD-Q590` | B | Исчезновение динамического объекта меняет его presence state; история сохраняется, а повторное появление той же stable source identity распознаётся как тот же объект. |

| `PRD-Q592` | B | Камера, дверь, сервер и аналогичный объект имеют одну общую core identity независимо от того, из какого сервиса они открыты. |

| `PRD-Q594` | B | Service-specific extension изменяется сервисом, которому принадлежит его семантика; общие поля объекта и специализированные поля имеют явных владельцев. |
| `PRD-Q595` | B | Удаление общего объекта проходит cross-service impact analysis и учитывает extensions, archive holds, dashboards, incidents, ТОиР, карты, automation references и другие зависимости. |
| `PRD-Q596` | B | Удаление специализированного пакета не удаляет автоматически core objects и пользовательскую историю; судьба extension определяется политикой удаления пакета. |
| `PRD-Q597` | B | Исторические ссылки на объект и его прежнюю специализированную семантику остаются осмысленными после decommission, удаления integration/package или замены оборудования. |
| `PRD-Q598` | B | Вводится минимальная общая сущность Person как долговечная ссылка на физического человека, но не как user account или HR-карточка. |
| `PRD-Q599` | принято | SCADA account, ACS subject, ТОиР executor, shift participant и notification contact могут ссылаться на одну Person, сохраняя собственную семантику и lifecycle. |
| `PRD-Q600` | B | Person не превращает «Диспетчер» в HR-систему; хранится только необходимый платформе минимум, а HR/ERP/directory могут оставаться внешними authoritative systems. |
| `PRD-Q601` | B | Деактивация Person запускает управляемую cross-domain policy для login, ACS credentials, новых ТОиР assignments, будущих смен и персональных уведомлений; история сохраняется. |
| `PRD-Q602` | B | Поддерживается быстрый offboarding/security action, инициирующий предусмотренные политики отключения связанных активных полномочий без удаления Person и истории. |
| `PRD-Q603` | B | Managed resource Edge и его authentication principal/certificate являются разными сущностями. |
| `PRD-Q604` | B | Между managed resource и authentication principal существует явная стабильная связь; то же относится к integration instance/service identity и другим machine identities. |
| `PRD-Q605` | B | При re-enrollment после компрометации resource identity Edge сохраняется, authentication principal заменяется, а старый principal отзывается. |
| `PRD-Q606` | B | Revoke или удаление principal не удаляет managed resource; их lifecycle независимы. |
| `PRD-Q607` | B | Индивидуально отслеживаемая серийная запасная часть сохраняет одну physical-unit identity через storage, installation, removal, repair и повторную установку. |
| `PRD-Q608` | B | Неиндивидуализированные материалы и расходники учитываются количественно как stock/material item; отдельная physical identity создаётся только при технической необходимости трассировки. |
| `PRD-Q609` | B | При замене физического устройства функциональный объект сохраняет identity, а installed physical unit меняется с историей интервалов установки. |
| `PRD-Q610` | B | Установка и снятие physical unit являются историческими эксплуатационными событиями, связанными с functional object, временем, работой ТОиР, исполнителем и причиной. |

## Runtime state, operational exceptions, time quality и counters

| ID | Вариант | Принятое решение |
|---|---:|---|
| `PRD-Q611` | B | Persistent storage Rule предназначен для внутреннего состояния исполнения, например debounce, state machine, последнего выбора или накопителя алгоритма, а не для скрытых долговременных настроек. |
| `PRD-Q612` | B | Rule не хранит в persistent storage authoritative эксплуатационный setpoint или политику; такие значения моделируются параметрами или managed configuration. |
| `PRD-Q613` | принято | Критерий границы: если изменение значения является изменением политики/настройки поведения системы для оператора или инженера, это configuration, а не внутренний runtime state Rule. |
| `PRD-Q614` | B | Persistent rule state имеет lifecycle совместимости с версией Rule: preserve, migrate, reset либо блокировка несовместимой публикации без migration. |
| `PRD-Q615` | B | Manual substitution, manual control, automation override, alarm suppression и maintenance остаются разными сущностями, но входят в общую модель operational exceptions. |
| `PRD-Q616` | B | Объект показывает единый effective operational context со всеми действующими исключениями и их влиянием. |
| `PRD-Q617` | B | Нет одного глобального линейного приоритета исключений; влияние разделяется по dimensions: value, control, automation, alarm handling, lifecycle/maintenance и notifications. |
| `PRD-Q618` | B | Maintenance не означает автоматическое подавление всех alarms; применяется опубликованная maintenance alarm policy с явными правилами для каждого класса alarm. |
| `PRD-Q619` | B | Manual control влияет на automation согласно control ownership policy, а не обязательно полностью останавливает все Rules. |
| `PRD-Q620` | B | Command Model учитывает effective control state и блокирует/ограничивает автоматическую команду к объекту под manual override с понятным результатом причины. |
| `PRD-Q621` | B | Временные operational exceptions поддерживают start, optional expiry, owner, reason и review/expiry notification; некоторые исключения могут быть постоянными по политике. |
| `PRD-Q622` | B | Поведение после expiry определяется типом исключения и опубликованной policy; не каждое состояние безопасно автоматически возвращать назад. |
| `PRD-Q623` | B | Открытая работа ТОиР и object lifecycle state maintenance являются разными сущностями. |
| `PRD-Q624` | B | Работа ТОиР не всегда автоматически переводит объект в maintenance; конкретный вид работы/технологическая карта может требовать или предлагать такой transition. |
| `PRD-Q625` | B | Alarm maintenance mode не равен object lifecycle maintenance; он может активироваться состоянием объекта, зоной работ, работой ТОиР или отдельным разрешённым действием. |
| `PRD-Q626` | принято | UI отдельно показывает object lifecycle, активную работу ТОиР, alarm maintenance policy, control mode и parameter substitutions, не скрывая их одним словом «обслуживание». |
| `PRD-Q627` | B | Для значимых Full, Edge, устройств, камер и внешних источников, где это возможно, отслеживается состояние качества времени. |
| `PRD-Q628` | принято | Time quality имеет общие категории trusted/synchronized, synchronized with known uncertainty, degraded, unsynchronized и unknown; при наличии сохраняются offset, uncertainty, last synchronization и time source. |
| `PRD-Q629` | B | Неверный source timestamp не переписывается незаметно; отдельно хранятся source time, receive/ingest time, time quality/offset и возможное производное corrected time. |
| `PRD-Q630` | B | Ordering событий при плохом source time использует предметную policy с time quality, receive order, sequence numbers и другими доступными данными. |
| `PRD-Q631` | B | Система может честно фиксировать неопределённый относительный порядок событий, если достоверную последовательность установить нельзя. |
| `PRD-Q632` | B | Потеря или деградация синхронизации времени является диагностируемым состоянием и по политике может создавать event/alarm и снижать доверие к SOE/correlation. |
| `PRD-Q633` | B | Тип counter имеет специальную семантику накопления и отличается от обычного analog value. |
| `PRD-Q634` | принято | Counter model различает normal increase, reset, rollover, replacement, correction и reverse/decrease, если последнее допустимо предметной моделью. |
| `PRD-Q635` | B | Любое уменьшение counter не трактуется автоматически как reset; используется объявленная counter policy. |
| `PRD-Q636` | B | Замена физического счётчика создаёт новый counter segment, связанный с replacement event, при сохранении функциональной точки учёта. |
| `PRD-Q637` | B | Агрегаты могут вычислять непрерывное потребление через segments, но сохраняют provenance resets/replacements/corrections/gaps. |
| `PRD-Q638` | B | Ошибочное counter value не переписывается; исходный факт сохраняется, а исправление оформляется отдельной governed correction. |

## Cross-domain sensitivity/privacy и лицензионная безопасность

| ID | Вариант | Принятое решение |
|---|---:|---|
| `PRD-Q639` | B | Платформа имеет компактный общий sensitivity/privacy policy layer для данных, переходящих между предметными сервисами. |
| `PRD-Q640` | B | Не вводится тяжёлая корпоративная DLP-классификация; используется небольшой расширяемый набор категорий/меток чувствительности. |

| `PRD-Q646` | B | Экспорт составного результата повторно проверяет права на исходные данные и право на операцию export; incident/report не становится обходом доступа. |
| `PRD-Q647` | B | Где предметная семантика позволяет, пользователь видит доступную часть составного объекта и явный факт наличия скрытых связанных данных без раскрытия их содержимого. |

| `PRD-Q650` | B | Sensitivity и retention являются разными dimensions, хотя политики могут быть связаны. |
| `PRD-Q651` | B | Privacy/deletion policy не разрушает immutable audit, investigation hold или обязательную эксплуатационную историю; действуют предметные retention/hold rules. |

| `PRD-Q656` | B | Коммерческие ограничения сохраняются для расширения системы: новые лицензируемые объекты, Edge/capacity, capabilities, packages и configuration changes, увеличивающие licensed usage. |
| `PRD-Q657` | B | При license exceed разрешены изменения существующей конфигурации, необходимые для ремонта и восстановления, если они не увеличивают лицензируемый объём. |
| `PRD-Q658` | B | Licensing учитывает lifecycle/replacement/HA/DR и не считает исторические или временно заменяемые сущности автоматическим коммерческим расширением. |
| `PRD-Q659` | принято | Фундаментальный инвариант: licensing никогда не ослабляет safety, security, audit integrity или recoverability существующего эксплуатационного контура. |
