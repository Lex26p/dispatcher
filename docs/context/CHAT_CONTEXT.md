# Контекст проекта для продолжения в новом чате

## Назначение файла

Этот файл предназначен для быстрого восстановления контекста обсуждения проекта «Диспетчер» в новой сессии ChatGPT или другом рабочем чате.

Репозиторий `Lex26p/dispatcher` является источником истины. Перед продолжением работы следует сначала прочитать `docs/README.md`, затем нужные concept-файлы.

## Что мы создаём

«Диспетчер» — универсальная модульная платформа диспетчеризации и управления оборудованием.

Общая идея: вентиляция, отопление, освещение, серверы, коммутаторы, CCTV, СКУД и другие системы имеют общий верхнеуровневый паттерн — мониторинг данных, события и команды управления. Ядро должно предоставлять универсальные механизмы, а конкретные предметные функции и протоколы подключаются как плагины.

CCTV и СКУД не следует называть разновидностями SCADA. Они рассматриваются как отдельные доменные модули над общим диспетчерским ядром.

## Основные продуктовые принципы

1. Ядро небольшое и универсальное.
2. Всё необязательное по возможности выносится в пакеты.
3. Если пакет не установлен, его функций не должно быть в интерфейсе.
4. Система предназначена и для инженеров, и для программистов.
5. Типовые задачи предпочтительно решаются через UI, но код является полноценным инструментом и не должен искусственно ограничиваться.
6. Не следует создавать отдельный специальный механизм для каждой мелочи, если задачу можно решить универсальными средствами.
7. Dashboard является основным универсальным механизмом построения Web UI и должен переиспользоваться там, где это естественно.
8. Концепцию не следует превращать в огромное ТЗ. Архитектуру обсуждаем после концепции.

## Согласованные сервисы ядра

- проекты;
- Dashboard;
- мнемосхемы;
- устройства;
- метрики;
- команды;
- диспетчер событий;
- пользователи и права;
- системные данные и базовое администрирование;
- менеджер пакетов;
- общий Web UI.

Автоматизация была первоначально рассмотрена как часть ядра, но затем сознательно вынесена в отдельный плагин, потому что без неё платформа всё ещё может выполнять базовый мониторинг, события и ручное управление.

## Проекты

Проект — точка консолидации, а не владелец данных.

Дашборды, мнемосхемы, устройства и другие элементы существуют независимо. Проект связывает их в единый контекст и используется для навигации и разграничения доступа.

Проекты не могут включать другие проекты.

Пользователь с доступом к нескольким проектам должен иметь возможность видеть объединённый диспетчер событий и фильтровать его по проектам.

## Dashboard

Dashboard — универсальная страница, собранная из контейнеров и компонентов.

Он является базовым механизмом Web UI и должен использоваться для системных и настроечных страниц, если это естественно.

Dashboard может получать параметры от проекта и передавать параметры вложенным компонентам. Возможны три базовых случая:

- ничего не передавать;
- задать параметры самому;
- делегировать параметры проекту.

Эти способы могут сочетаться.

Dashboard отвечает за страницы, контейнеры, модальные окна и навигацию.

## Мнемосхемы

Мнемосхема — интерактивное SVG-изображение с данными, состояниями, анимациями и действиями.

Она существует как отдельный редактируемый ресурс, но отображается только внутри контейнера Dashboard.

Мнемосхема не является отдельной Web-страницей, не создаёт собственные модальные окна и не содержит «другую мнемосхему внутри себя».

Переиспользование решается параметрами, шаблонами и библиотечными SVG-элементами.

## Устройства, метрики и команды

Устройство — универсальный объект диспетчеризации. Оно может соответствовать физическому оборудованию или быть виртуальным, но пользователю не нужно навязывать отдельную классификацию физическое/виртуальное.

Метрика — универсальная единица данных. Она может относиться к устройству или существовать самостоятельно, приходить от оборудования или вычисляться.

Команда — отдельное от метрики действие управления.

Шаблон устройства используется только при создании. После создания устройство независимо от дальнейших изменений шаблона.

## Диспетчер событий

Единый глобальный сервис для событий, аварий, предупреждений, значимых действий пользователей и системных проблем.

Аварии и обычные события отображаются вместе, чтобы сохранялась временная цепочка, но авария может иметь жизненный цикл и подтверждение.

Проект — контекст и фильтр, а не отдельный экземпляр диспетчера событий.

## Пользователи и права

Различаются просмотр, управление, редактирование/настройка и административные права.

Пользователь может иметь разные права в разных проектах.

Есть опциональный режим управления — защита от случайных команд. Если у пользователя нет права управления, он не может включить режим управления. Если право есть, режим может включаться временно и автоматически отключаться.

## Системные данные

Показатели самой платформы — CPU, RAM, диск, uptime, состояния компонентов — рассматриваются как обычные метрики.

Значимые системные проблемы попадают в общий диспетчер событий.

Технические подробные логи остаются отдельным административным инструментом.

## Менеджер пакетов

Единая точка для плагинов, драйверов, шаблонов, компонентов и обновлений.

Базовые действия: установить, обновить, отключить, включить, удалить.

Должны поддерживаться общий каталог и ручная установка пакетов.

Обновления платформы и пакетов видны в одном сервисе. Автоматическая установка обновлений не обязательна.

## Web UI

Основной каркас:

- компактный глобальный Header;
- слева в Header — «бутерброд» глобальной навигации;
- справа — колокольчик диспетчера событий, конверт сообщений пользователя, пользовательское меню;
- у сервиса может быть своя левая навигация;
- справа — панель свойств;
- по центру — максимально большая рабочая область;
- локальный Header сервиса используется только при необходимости;
- Footer используется только если нужен.

Редко используемые ссылки не должны постоянно занимать место на экране.

## Автоматизация как первый планируемый плагин

Автоматизация включает визуальные сценарии, JavaScript и планировщик.

Она не входит в ядро. Без неё система остаётся рабочей, хотя смещается ближе к мониторингу и ручному управлению.

Отдельный концептуальный файл: `docs/plugins/automation/concept.md`.

## Как ведём дальнейшее обсуждение

Рабочий процесс согласован следующим образом:

1. Берём одну крупную тему.
2. ChatGPT задаёт небольшой блок концептуальных вопросов и предлагает свои ответы.
3. Пользователь соглашается или корректирует.
4. Не уходим в архитектуру и мелкое ТЗ раньше времени.
5. После согласования крупного блока решения фиксируются в репозитории.
6. Количество тем может меняться по мере необходимости.

## Работа с файлами и Git

Пользователь хочет получать изменения архивом, который распаковывает поверх локального репозитория PowerShell-командой `Expand-Archive`.

После этого ChatGPT выдаёт одним блоком команды Git для проверки, коммита, push и получения SHA коммита. Пользователь отправляет SHA обратно в чат, и этот commit становится новой базовой точкой для дальнейшей работы.

Репозиторий: `https://github.com/Lex26p/dispatcher`.
