# Архитектурные решения

Этот файл фиксирует принятые решения, чтобы следующие изменения не основывались на догадках.

Если решение меняется, старое не удаляется молча: его статус меняется на `Superseded`, а ниже добавляется новое решение с причиной.

---

## D-001 — C#/.NET для Core и Server

**Status:** Accepted

Core и Server реализуются на C#/.NET.

Причина:

- хороший async/I/O стек;
- удобная строгая типизация;
- естественная модель фоновых сервисов;
- возможность развивать polling и протокольные компоненты без раннего перехода на C++;
- единый основной язык backend-части.

C++ не планируется как обязательный следующий этап. Native-компоненты рассматриваются только при доказанной необходимости.

---

## D-002 — Blazor WebAssembly для Web

**Status:** Accepted

Web-клиент реализуется на Blazor WebAssembly.

Причина:

- C# на клиенте и сервере;
- возможность разделять контрактные типы;
- клиентский UI исполняется в браузере;
- подходит для операторского приложения, которому не требуется SEO.

Для сложной графики в будущем допускается JavaScript interop без отказа от Blazor в остальной части приложения.

---

## D-003 — TagService как центр runtime-состояния

**Status:** Accepted

Центральной runtime-абстракцией является логический Tag.

`TagService` хранит текущее состояние и является общей точкой доступа к нему.

Он не должен зависеть от Modbus/SNMP деталей.

---

## D-004 — Протокольные детали изолированы

**Status:** Accepted

Web, мнемосхемы и общая предметная логика обращаются к логическим `TagId`.

Прямые зависимости верхних уровней от Modbus-register, coil, SNMP OID и других protocol-specific адресов запрещены.

---

## D-005 — Начинать просто

**Status:** Accepted

Не строим заранее полноценную SCADA.

До отдельной необходимости не вводим:

- alarms;
- events;
- roles;
- historian;
- message broker;
- distributed services;
- сложный plugin runtime.

Сначала создаётся работающий вертикальный срез.

---

## D-006 — Логическая модульность раньше физического разделения

**Status:** Accepted

Core, Server и протокольные компоненты проектируются с явными границами, но в ранней версии могут выполняться в одном серверном процессе.

Отдельные процессы или сетевые сервисы вводятся только при фактической необходимости.

---

## D-007 — REST + SignalR

**Status:** Accepted

Для Web:

- REST используется для получения начального состояния и команд;
- SignalR используется для realtime-изменений.

SignalR не заменяет весь API.

---

## D-008 — Configuration и Runtime разделены

**Status:** Accepted

Постоянная конфигурация устройства/тега не смешивается с текущими runtime-значениями.

На раннем этапе runtime может храниться в памяти.

Постоянное хранилище конфигурации добавляется на этапе редактора устройств.

---

## D-009 — Репозиторий является источником истины

**Status:** Accepted

Перед каждым шагом разработки агент обязан читать актуальный `master` репозитория и необходимые файлы.

Содержимое прошлых сообщений не имеет приоритета над текущим состоянием репозитория.

Правила взаимодействия подробно описаны в корневом `AGENTS.md`.

---

## D-010 — Web как плотный инженерный интерфейс

**Status:** Accepted

Web-интерфейс проектируется с приоритетом рабочей области и информационной плотности.

Базовая компоновка:

- один компактный глобальный header;
- кнопка `☰` слева открывает глобальную навигацию между сервисами;
- глобальная навигация не должна постоянно занимать рабочее пространство;
- внутри выбранного сервиса слева постоянно расположена локальная навигация;
- в центре находится основная рабочая область;
- справа находятся свойства выбранного объекта;
- второй компактный contextual header/toolbar допустим только при необходимости;
- устройства и аналогичные сущности отображаются преимущественно списками/таблицами;
- важные operational-состояния не скрываются ради декоративного минимализма.

Причина:

Dispatcher — инженерный рабочий инструмент. Пространство экрана должно использоваться для данных, редактирования и управления, а не для декоративной структуры типичного публичного Web-приложения.

Подробные UI-правила зафиксированы в `docs/WEB_UI.md`.
