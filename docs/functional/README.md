# Функциональная спецификация Dispatcher

**Статус:** рабочий канонический слой требований между общей продуктовой концепцией и системной архитектурой.  
**Дата начала этапа:** 7 августа 2026 года.

## 1. Назначение

Общая продуктовая концепция отвечает на вопрос **что такое Dispatcher и какими фундаментальными правилами он живёт**. Функциональная спецификация отвечает на следующий вопрос:

> **Как Dispatcher должен работать с точки зрения пользователя, роли, предметного процесса и наблюдаемого поведения системы?**

Этот слой уже достаточно конкретен для последующего проектирования UX, API и программной архитектуры, но не фиксирует способы реализации.

В функциональной спецификации допустимы и ожидаются:

- пользовательские роли и рабочие сценарии;
- рабочие области, реестры, редакторы и действия;
- состояния сущностей и переходы между ними;
- правила видимости, доступности и объяснимости действий;
- функциональные проверки и ошибки;
- взаимодействие Full / Compact / Edge на уровне наблюдаемого поведения;
- требования к realtime-поведению интерфейса;
- функциональные требования к импорту, публикации, командам, alarm handling и другим процессам;
- сквозные сценарии от инженерной настройки до эксплуатации.

В этом слое **не фиксируются**, если отдельное решение не требуется именно как функциональный контракт:

- язык программирования;
- frontend/backend framework;
- таблицы БД;
- внутренние service boundaries;
- message broker;
- конкретный transport/API protocol;
- fencing/lease/consensus implementation;
- схема deployment-инфраструктуры;
- конкретные алгоритмы persistence/cache.

## 2. Источники истины

При работе над функциональными требованиями используются:

1. [`../product/PRODUCT_CONCEPT.md`](../product/PRODUCT_CONCEPT.md) — общая продуктовая концепция.
2. [`../product/PRODUCT_DECISIONS.md`](../product/PRODUCT_DECISIONS.md) — действующие продуктовые решения `PRD-Q001–PRD-Q803`.
3. [`REFERENCE_SCENARIOS.md`](REFERENCE_SCENARIOS.md) — сквозные сценарии, которыми проверяется согласованность спецификаций.
4. Предметный functional-spec файл — источник истины по конкретной функциональной области.
5. [`ROADMAP.md`](ROADMAP.md) — временный навигатор текущего этапа; не является источником требований.

При противоречии functional requirement с общей концепцией сначала решается противоречие. Функциональная спецификация не имеет права молча отменять фундаментальный PRD.

Внутри предметной спецификации:

- `<AREA>-Q001...` — обсуждаемый продуктово-функциональный вопрос;
- `<AREA>-FR001...` — принятое функциональное требование.

После принятия решения его смысл переносится в функциональные требования соответствующего файла. Не создаётся отдельный глобальный журнал решений только ради истории обсуждения.

## 4. Принцип детализации

Требование должно описывать наблюдаемое поведение продукта достаточно точно, чтобы позднее можно было:

- спроектировать экран/UX;
- определить API contract;
- написать acceptance tests;
- проверить поведение Full/Compact/Edge;
- понять права и ошибки;
- не гадать о смысле сущности при реализации.

При этом не следует преждевременно проектировать внутреннюю реализацию.

Пример подходящего требования:

> Инженер должен видеть различие между опубликованной desired configuration и фактически активированной конфигурацией Edge, включая причину расхождения и состояние доставки/активации.

Пример слишком архитектурного требования для этого этапа:

> Состояние Edge хранится в PostgreSQL и доставляется через NATS JetStream.

Новые папки создаются только при фактическом начале соответствующей спецификации. Пустой каталог документов «на будущее» не поддерживается.

## 6. Рабочий цикл области

1. Определить границы и reference scenarios.
2. Разобрать вопросы `<AREA>-Q...` небольшими раундами.
3. Свести принятые решения в `<AREA>-FR...`.
4. Проверить требования по `REFERENCE_SCENARIOS.md` и соседним областям.
5. Провести короткий consistency review.
6. Перевести область в `DONE` в `ROADMAP.md`.
7. Зафиксировать checkpoint в Git.

## 7. Условие перехода к архитектуре

Не требуется закончить функциональное ТЗ абсолютно всех сервисов до начала архитектуры.

Первый architecture-readiness gate наступает после достаточной детализации трёх центральных областей:

1. Engineering / Configuration;
2. Operations / Dispatcher Workspace;
3. Web Platform.

Они должны дать устойчивый сквозной контур:

> инженер создаёт и публикует конфигурацию → runtime/Edge её исполняет → диспетчер видит live state/alarm → выполняет semantic command → результат и audit возвращаются в продукт.

После этого можно проектировать системную архитектуру платформы, продолжая детализировать остальные функциональные области на уже устойчивом фундаменте.

## 8. Завершение этапа

`ROADMAP.md` — временный файл. Когда функциональный этап завершён и его состояние перенесено в постоянные канонические документы следующего этапа, `ROADMAP.md` удаляется. История остаётся в Git.
