# Внешний контракт Data Hub

## Статус

Базовый контракт зафиксирован в `CORE-001 / Step 2`.

Поведение публикации, чтения, подписок и state-метрик последовательно уточняется внутри `CORE-001`, не меняя границы ответственности Data Hub.

Этот документ описывает только внешний транспортный контракт Data Hub. Он не определяет транспорт Event Hub или Service Hub.

## Выбранные технологии

Для внешнего взаимодействия с Data Hub используются:

- **gRPC** как транспорт RPC и streaming;
- **Protocol Buffers proto3** как схема и формат сериализации;
- versioned protobuf package `dispatcher.data_hub.v1`.

Контракт хранится в репозитории рядом с сервисом:

`services/data-hub/proto/dispatcher/data_hub/v1/data_hub.proto`

Сгенерированный C++ код не хранится в Git и создаётся во время сборки.

## Почему контракт отделён от внутренних C++ классов

Другие сервисы не должны подключаться к внутренним классам Data Hub.

`.proto` является межсервисным контрактом и позволяет:

- независимо менять внутреннюю реализацию Data Hub;
- генерировать клиенты и серверные интерфейсы;
- использовать тот же контракт из других языков в будущем;
- эволюционно расширять сообщения, не меняя смысл существующих protobuf field numbers.

## Минимальная поверхность RPC

На первом этапе контракт содержит четыре операции:

### PublishMetric

Источник публикует фактическое текущее значение метрики.

Это не запрос управления.

### GetCurrent

Клиент запрашивает текущее значение метрики.

Если текущее значение неизвестно Data Hub, текущая реализация возвращает gRPC `NOT_FOUND`.

### Subscribe

Клиент подписывается на явно перечисленные метрики и получает stream обновлений.

Новый подписчик получает уже существующие текущие значения запрошенных метрик, после чего получает их дальнейшие изменения.

Пустой список не означает «подписаться на всё» и считается некорректным запросом.

### WriteMetric

Клиент запрашивает изменение значения writable-метрики.

`WriteMetric` намеренно отделён от `PublishMetric`:

- `PublishMetric` сообщает Data Hub фактическое текущее значение;
- `WriteMetric` выражает запрос изменить значение через будущего владельца/провайдера метрики.

Маршрут до Driver Runtime и конкретного драйвера реализуется в следующих шагах.

## MetricId

Идентификатор метрики передаётся отдельным сообщением `MetricId` со строковым значением.

Для Data Hub идентификатор непрозрачен.

Data Hub не должен извлекать из строки:

- устройство;
- проект;
- расположение;
- протокол;
- тип метрики;
- другие предметные данные.

Конкретные соглашения по формированию идентификаторов могут развиваться отдельно.

## MetricValue

Тип значения определяется активной веткой protobuf `oneof`.

Первый контракт поддерживает:

- `bool`;
- `int64`;
- `uint64`;
- `double`;
- `string`;
- `bytes`.

Не вводится отдельное дублирующее поле `value_type`, которое могло бы расходиться с реально заполненной веткой `oneof`.

Новые типы могут быть добавлены в будущем как новые поля `oneof` с новыми field numbers.

## Runtime-метаданные

`MetricSample` содержит:

- `metric_id`;
- `value`;
- `source_timestamp_unix_ms`.

`source_timestamp_unix_ms` — время источника в миллисекундах Unix epoch.

Значение `0` означает, что источник не предоставил timestamp.

Семантика quality, время приёма Data Hub и другие дополнительные runtime-поля пока не фиксируются. Protocol Buffers позволяет добавить их позже без изменения существующих номеров полей.

## State-метрики

State-метрика использует тот же `MetricSample`, `PublishMetric`, `GetCurrent` и `Subscribe`, что и любая другая метрика.

Концептуальный пример:

    AHU01.Temperature       = 26.0
    AHU01.Temperature.State = Alarm

Важно: `.State` в примере не является правилом протокола Data Hub.

Data Hub не должен:

- определять state-метрику по синтаксису `MetricId`;
- вычислять состояние рабочей метрики;
- фиксировать окончательный enum состояний;
- хранить описательную связь рабочей метрики со state-метрикой.

Такое разделение сохраняет Data Hub универсальным runtime-хранилищем.

Диспетчер событий/аварий позднее публикует рассчитанное состояние как значение соответствующей state-метрики.

Связь рабочей метрики с её state-метрикой относится к описательной модели метрик и должна быть задана там, где хранится эта модель, а не дублироваться в каждом runtime sample Data Hub.

## Что не входит в контракт Data Hub

В runtime-контракт не помещаются описательные данные, принадлежащие Device Manager, например:

- название устройства;
- описание;
- расположение;
- единица измерения;
- writable/read-only настройка;
- связь рабочей метрики со state-метрикой;
- проектная принадлежность.

Также Data Hub contract не определяет:

- пользователей;
- права доступа;
- Event Hub;
- жизненный цикл аварий;
- историю значений;
- конкретный протокол оборудования.

## Текущая реализация CORE-001

К завершению `CORE-001 / Step 6` через реальную gRPC-границу проверены:

- публикация текущего значения;
- получение текущего значения;
- retained-подобная подписка;
- live updates;
- одинаковая работа этих механизмов для рабочей метрики и state-метрики.

Следующий шаг `CORE-001 / Step 7` реализует базовый путь `WriteMetric`.
