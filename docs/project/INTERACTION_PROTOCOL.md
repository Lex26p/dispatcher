# Протокол взаимодействия по проекту «Диспетчер»

**Статус:** действующий.  
**Дата первоначальной редакции:** 6 августа 2026 года.  
**Репозиторий:** `https://github.com/Lex26p/dispatcher`.  
**Рабочая ветка:** `master`.

## 1. Назначение

Документ определяет практический порядок совместной работы пользователя и AI-ассистента. Его задача — обеспечить воспроизводимую передачу изменений, понятную фиксацию решений и возможность без потери контекста перейти в другой чат или к другой модели.

Документ не описывает продуктовую концепцию, дорожную карту, архитектуру или программную реализацию «Диспетчера».

## 2. Основной принцип

Репозиторий является долговременной памятью проекта. Чат используется для обсуждения и подготовки изменений.

Работа всегда продолжается от конкретного полного SHA коммита, который пользователь прислал после предыдущего обновления.

## 3. Стандартный рабочий цикл

### Шаг 1. Получение исходной точки

Пользователь сообщает полный SHA актуального коммита. Ассистент использует этот коммит как основу следующей работы и читает из него необходимые файлы.

### Шаг 2. Обсуждение

Пользователь и ассистент обсуждают одну выбранную тему. Ассистент задаёт вопросы, предлагает варианты и рекомендуемое решение. Пользователь выбирает вариант или формулирует собственный ответ.

Обсуждение продолжается столько раундов, сколько требуется для снятия существенных неопределённостей.

### Шаг 3. Фиксация результата

После завершения согласованного объёма ассистент:

- создаёт или обновляет целевые файлы;
- обновляет состояние проекта;
- фиксирует принятые решения;
- фиксирует открытые вопросы;
- добавляет межтематические заметки;
- проверяет внутреннюю согласованность подготовленного комплекта.

### Шаг 4. Подготовка архива

Ассистент создаёт ZIP-архив, структура которого совпадает со структурой репозитория.

Требования к архиву:

- без каталога `.git`;
- без дополнительной корневой папки;
- с полными итоговыми версиями файлов;
- с понятным именем и номером редакции.

### Шаг 5. Применение архива

Ассистент выдаёт одну однострочную команду:

```powershell
Expand-Archive -Path "C:\Users\pereverworkki\Downloads\<archive>.zip" -DestinationPath "C:\Projects\dispatcher" -Force
```

Пользователь выполняет её в терминале Visual Studio.

Если изменение удаляет или переименовывает файлы, ассистент перед командой распаковки предоставляет необходимые однострочные команды `Remove-Item`.

### Шаг 6. Фиксация в Git

Ассистент выдаёт команды одним блоком:

```powershell
Set-Location "C:\Projects\dispatcher"
git status
git add -A
git commit -m "<сообщение коммита>"
git push
git rev-parse HEAD
```

Пользователь выполняет команды без ручного изменения подготовленных файлов.

### Шаг 7. Подтверждение

Пользователь присылает полный SHA, полученный командой `git rev-parse HEAD`.

Этот SHA становится исходной точкой следующего рабочего цикла.

## 4. Разделение ответственности

### Пользователь принимает решения

Пользователь определяет целевой продукт, утверждает варианты и может заменить рекомендацию ассистента собственным решением.

### Ассистент ведёт содержимое

Только ассистент формирует и изменяет текст и код. Это позволяет считать локальную копию после распаковки и облачный репозиторий после `git push` идентичными.

### Пользователь выполняет техническую доставку

Пользователь распаковывает архив и отправляет изменения в Git. Ассистент не выполняет прямые записи в репозиторий, пока это правило явно не изменено.

## 5. Обсуждение тем

### Размер темы

Тема должна быть небольшой самостоятельной продуктовой проблемой. Крупный сервис является областью и разбивается на несколько тем.

### Формат вопроса

Для значимого вопроса ассистент указывает:

- суть вопроса;
- зачем требуется решение;
- возможные варианты;
- последствия вариантов;
- рекомендуемый вариант;
- причины рекомендации;
- связь с другими темами.

### Ответ пользователя

Пользователь может:

- выбрать вариант;
- выбрать вариант с изменениями;
- объединить варианты;
- предложить собственное решение;
- оставить комментарий;
- отложить вопрос.

### Дополнительные вопросы

После каждого ответа ассистент анализирует последствия. Если ответ открывает новые существенные неопределённости, ассистент формирует следующий раунд вопросов.

Количество вопросов и раундов не ограничивается.

## 6. Полнота концепций

Во время разработки концепций описывается зрелый целевой продукт целиком.

На этой стадии не вводятся:

- MVP;
- первая версия;
- поздние релизы;
- очереди программной реализации;
- упрощение целевого поведения ради более лёгкого начала разработки.

Порядок реализации будет определён отдельно перед написанием кода.

## 7. Передача работы другой модели

Для продолжения пользователь сообщает новой модели:

```text
Репозиторий: https://github.com/Lex26p/dispatcher
Ветка: master
Актуальный коммит: <полный SHA>
Начни с AGENTS.md и docs/project/PROJECT_STATE.md.
```

Новая модель должна:

1. прочитать `AGENTS.md`;
2. прочитать `PROJECT_STATE.md`;
3. прочитать связанные решения, вопросы и заметки;
4. изучить необходимые канонические документы;
5. продолжить с указанной в состоянии точки;
6. не восстанавливать проектные решения по догадкам из общей предметной области.

## 8. Состав служебных файлов

### `AGENTS.md`

Обязательные инструкции для любой модели: источник истины, роли, формат архивов, Git-команды, правила обсуждения и передачи контекста.

### `PROJECT_STATE.md`

Короткое актуальное состояние: подтверждённый SHA, текущая тема, завершённый объём, точка остановки и следующее действие.

### `DECISIONS.md`

Утверждённые решения. Рекомендации ассистента без согласия пользователя сюда не попадают.

### `OPEN_QUESTIONS.md`

Вопросы, которые сформулированы, но сознательно оставлены без решения.

### `AI_WORK_NOTES.md`

Межтематические наблюдения и напоминания, которые важно сохранить, но которые пока не являются решениями или полноценными открытыми вопросами.

## 9. Правила обновления служебных файлов

При каждом содержательном пакете ассистент проверяет необходимость обновить:

- текущий SHA и точку продолжения;
- статус активной темы;
- новые решения;
- новые открытые вопросы;
- межтематические зависимости и заметки.

Исторические записи не удаляются без причины. Если решение или заметка устарели, их статус меняется и добавляется ссылка на заменившую запись.

## 10. Ограничения текущего шага

На текущем шаге создаются только документы взаимодействия и передачи контекста.

Не создаются:

- дорожная карта;
- продуктовые концепции сервисов;
- архитектурные документы;
- требования;
- исходный код.
