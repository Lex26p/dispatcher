## 1. Текущий режим

Общая продуктовая концепция зрелой универсальной модульной SCADA-платформы «Диспетчер» достигла достаточного горизонтального охвата для сквозной проверки. Дорожная карта, программная архитектура, технологический стек и код по-прежнему не формируются до завершения этой проверки и отдельного решения о планировании реализации.

## 2. Зафиксированный объём

Редакция 3 сохраняет все решения предыдущих срезов и дополнительно фиксирует:

- интеграции и публичный API: `PRD-Q305–PRD-Q337`;
- secure-by-default, секреты, сертификаты, PKI, сетевые интерфейсы и security events: `PRD-Q338–PRD-Q365`;
- диагностику, backup/restore, HA, RPO/RTO и disaster recovery: `PRD-Q366–PRD-Q398`;
- развёртывание, обновления, offline delivery и лицензирование: `PRD-Q399–PRD-Q437`;
- полноценный VMS: `PRD-Q438–PRD-Q473`;
- встроенную offline-справку и документацию продукта: `PRD-Q474–PRD-Q501`;
- общие границы специализированных сервисов и предметных областей: `PRD-Q502–PRD-Q527` с пользовательскими заменами `PRD-Q517R`, `PRD-Q518R`, `PRD-Q521R`, `PRD-Q522R`.

Суффиксы `R` и `N` обозначают итоговые заменяющие решения после пересмотра прежней формулировки. Отвергнутые черновые варианты не являются продуктовыми решениями.

## 3. Ключевые новые принципы

### API и безопасность

Внешние интеграции используют предметные API и service identities и не обходят права, Command API или Draft → Validate → Approve → Publish. Публичные API выключаемы по группам возможностей из веб-интерфейса и публикуются только на нужных сетевых интерфейсах. Выключенный API по возможности вообще не имеет внешнего listener/route. Секреты и сертификаты управляются централизованно, Full↔Edge взаимно аутентифицированы, а security posture установки проверяется явно.

### Надёжность и эксплуатация платформы

Диагностика объясняет эксплуатационные последствия с раскрываемой технической причиной. Backup является согласованным проверяемым артефактом и может тестироваться восстановлением. Full поддерживает HA без split-brain, Edge сохраняет автономность, установка имеет RPO/RTO и DR-plan. Обновления проходят preflight и recovery plan, работают в закрытой сети через подписанные offline packages. Лицензирование полностью offline и не останавливает действующий операторский контур при коммерческом нарушении.

### VMS

VMS является полноценным специализированным сервисом с live, архивом, timeline, PTZ, видеостенами, аналитикой, retention и доказательным экспортом. Он может владеть видеоконтуром сам или интегрироваться с внешними VMS/NVR. Камеры остаются общими управляемыми объектами и связываются с СКУД, оборудованием, авариями и планами.

### Документация продукта

Встроенная справка полностью доступна offline, соответствует установленной версии и включает документацию пакетов, API, troubleshooting, коды ошибок, примеры, пошаговые инструкции, release notes и migration guidance. Системная справка не смешивается с пользовательскими документами организации.

### Границы сервисов

Отдельный сервис создаётся только при наличии собственного устойчивого процесса и специализированного рабочего пространства. Пожарные системы не выделяются в отдельный сервис и используют обычные предметные дашборды и планы. СКУД охватывает любые физические точки доступа, включая шлагбаумы, ворота и турникеты, а специализированный сервис нужен для субъектов и политик доступа. Серверы и сетевое оборудование являются полноценной областью диспетчеризации общей SCADA; обязательный отдельный NMS-сервис не фиксируется.

## 5. Точка продолжения

Следующий этап — **сквозная проверка общей продуктовой концепции**. Проверка должна искать противоречия между решениями, дублирование сущностей и сервисов, неоправданно сложные механизмы, терминологические расхождения, недостающие фундаментальные функции и несогласованные границы Full/Compact/Edge.

После общей проверки каждую крупную предметную область нужно обсуждать отдельно и подробно: HVAC, энергетика/энергоучёт, пожарные системы, СКУД, BIM, карты/планы, IT и сети, вода/насосы, освещение, лифты/эскалаторы, VMS, ТОиР и другие области. Текущие границы являются общей гипотезой и могут уточняться предметной концепцией.

Перед проверкой читать `AGENTS.md`, настоящий файл, `docs/product/PRODUCT_CONCEPT.md`, `PRODUCT_DECISIONS.md` и при необходимости тематические документы. Не восстанавливать решения по истории чата.

## 6. Действующие ограничения работы

- Не использовать отменённый черновик дорожной карты.
- Не определять очередность реализации внутри продуктовой концепции.
- Не обозначать функции «будущими» только ради упрощения концепции.
- Не смешивать продуктовый сервис с программным микросервисом.
- Не считать отдельную инженерную область автоматическим основанием для отдельного сервиса.
- Не тратить контекст на исчерпывающую проверку каждого подтверждённого коммита без причины.
