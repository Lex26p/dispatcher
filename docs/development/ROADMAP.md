# Дорожная карта проекта «Диспетчер»

## Назначение

Этот файл задаёт направление разработки проекта и используется как рабочая карта для последовательного движения по крупным этапам, спринтам и шагам.

Дорожная карта нужна не для фиксации сроков, а для того, чтобы в каждой рабочей сессии было понятно:

- что сейчас разрабатывается;
- зачем это делается;
- какой результат должен быть получен;
- что не относится к текущей задаче.

Репозиторий является источником истины. Если обсуждение приводит к изменению направления разработки, соответствующее изменение должно быть отражено в этом файле.

---

## Три уровня планирования

### Уровень 1 — этап развития продукта

Крупное законченное направление разработки.

Все этапы первого уровня определяются заранее. Для каждого этапа фиксируются:

- цель;
- что входит в этап;
- какой результат должен быть получен;
- состояние этапа.

Этап первого уровня не расписывается сразу до мелких задач.

### Уровень 2 — спринт

Спринт — законченная часть текущего этапа первого уровня.

Спринты конкретного этапа определяются **непосредственно перед началом этого этапа**.

Для каждого спринта должны быть определены:

- что именно разрабатывается;
- зачем это нужно текущему этапу;
- ожидаемый результат;
- критерий завершения.

Спринт должен иметь проверяемый результат. Формулировки вида «поработать над Data Hub» не используются.

### Уровень 3 — шаг

Шаги определяются **непосредственно перед началом конкретного спринта**.

Шаг описывает конкретное действие, необходимое для достижения результата спринта.

Шаги не следует детализировать заранее для будущих спринтов, потому что фактическая разработка может изменить понимание следующей работы.

---

## Правила изменения плана

Дорожная карта является направляющей, но не неизменяемой.

Допускается:

- добавить шаг, если без него невозможно корректно завершить спринт;
- разделить слишком крупный шаг на несколько;
- объединить шаги, если это упрощает работу;
- изменить состав будущих спринтов после получения новой информации;
- изменить порядок будущих этапов первого уровня, если появилась объективная причина.

Не следует:

- расширять текущий спринт функциями, которые не нужны для его результата;
- добавлять работу только потому, что «раз уж мы здесь, можно сделать ещё и это»;
- детализировать далёкие этапы раньше времени;
- менять цель текущего спринта без явной необходимости.

Если в процессе разработки обнаружена новая задача, которая не нужна для завершения текущего спринта, она должна быть отложена в подходящий будущий спринт или этап.

---

## Отчёты по спринтам

Для каждого спринта создаётся отдельный файл в:

`docs/development/sprints/`

Рекомендуемое имя:

`<SPRINT-ID>.md`

Например:

`CORE-003.md`

Файл спринта создаётся перед его началом и содержит:

- цель;
- ожидаемый результат;
- критерий завершения;
- согласованные шаги.

После завершения в этот же файл добавляются:

- что фактически реализовано;
- какие отклонения от первоначального плана были сделаны и почему;
- результат проверки;
- известные ограничения;
- итоговый commit SHA.

Таким образом один файл является одновременно планом и итоговым отчётом спринта.

# Этапы первого уровня

## L1-01 — Ядро платформы

**Статус:** следующий этап разработки.

### Цель

Создать самодостаточную универсальную платформу диспетчеризации, которая уже способна работать с реальным оборудованием и служить основой для всех последующих плагинов.

### В этап входит

На уровне продукта и архитектуры ядро должно включить и довести до работоспособного состояния:

- общую структуру backend на C++;
- Data Hub;
- Event Hub;
- Service Hub;
- Device Manager;
- устройства и метрики;
- записываемые метрики;
- state-метрики;
- диспетчер событий / аварий;
- проекты;
- пользователей и права доступа;
- режим управления;
- Package Manager;
- общий Web UI;
- Dashboard;
- мнемосхемы;
- базовую драйверную инфраструктуру;
- драйвер Modbus;
- драйвер SNMP;
- необходимые общие библиотеки проекта.

Modbus и SNMP разрабатываются вместе с ядром, чтобы ядро проверялось не только на искусственных данных, но и на реальном взаимодействии с оборудованием.

Дополнительные протоколы в этот этап не входят, если они не станут объективно необходимы для завершения ядра.

### Результат этапа

Должна существовать работоспособная система, в которой можно:

- подключить оборудование через Modbus и SNMP;
- создать или настроить устройства и их метрики;
- получать текущие значения через Data Hub;
- хранить в Data Hub актуальные значения и state-метрики;
- записывать значения в метрики, для которых разрешено управление;
- видеть данные в Web UI;
- использовать Dashboard и мнемосхемы;
- формировать и отображать события и аварии;
- разграничивать доступ пользователей;
- работать с проектами;
- устанавливать и управлять пакетами;
- расширять систему без переработки архитектуры ядра.

После завершения этого этапа «Диспетчер» должен быть полезной самостоятельной системой даже без плагинов автоматизации и истории.

### Спринты

Будут определены непосредственно перед началом этапа.

## L1-02 — Плагин автоматизации

**Статус:** запланирован.

### Цель

Добавить к платформе автоматическую реакцию на данные и события без переноса этой логики в ядро.

### В этап входит

- визуальные правила и сценарии;
- JavaScript как полноценный инструмент сложной логики;
- планировщик;
- запуск сценариев по событиям, значениям метрик, расписанию и вручную;
- взаимодействие автоматизации с общими механизмами платформы.

### Результат этапа

Пользователь должен иметь возможность создавать автоматическую логику поверх существующих устройств, метрик и событий как через визуальные средства, так и через JavaScript.

Автоматизация должна работать как устанавливаемый плагин и не требовать изменения архитектуры ядра.

### Спринты

Будут определены непосредственно перед началом этапа.

---

## L1-03 — Плагин истории

**Статус:** запланирован.

### Цель

Добавить долговременное хранение и использование исторических данных без превращения Data Hub в историческую БД.

### В этап входит

- сохранение истории выбранных метрик;
- получение исторических данных;
- настройка хранения;
- использование истории другими сервисами и Web UI;
- исторические графики и тренды как компоненты платформы.

### Результат этапа

Пользователь должен иметь возможность выбирать данные для архивирования, получать историю за нужный период и использовать её в Dashboard, графиках и других расширениях.

Плагин истории должен использовать общие контракты системы и оставаться независимым от ядра.

### Спринты

Будут определены непосредственно перед началом этапа.

### Цель

Создать отдельный предметный модуль видеонаблюдения поверх общего диспетчерского ядра.

Будут определены непосредственно перед началом этапа.

### В направление могут входить

- библиотеки мнемосхем;

- другие расширения.

### Результат этапа

Платформа должна иметь устойчивую модель развития, при которой новые возможности можно добавлять и распространять как пакеты без переработки основного ядра.

### Спринты

Будут определены непосредственно перед началом этапа.
