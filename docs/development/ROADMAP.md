# Дорожная карта проекта «Диспетчер»

## Назначение

Этот файл задаёт направление разработки проекта и используется как рабочая карта для последовательного движения по крупным этапам, спринтам и шагам.

Дорожная карта нужна не для фиксации сроков, а для того, чтобы в каждой рабочей сессии было понятно:

- что сейчас разрабатывается;
- зачем это делается;
- какой результат должен быть получен;
- что не относится к текущей задаче.

Репозиторий является источником истины. Если обсуждение приводит к изменению направления разработки, соответствующее изменение должно быть отражено в этом файле.

---

## Три уровня планирования

### Уровень 1 — этап развития продукта

Крупное законченное направление разработки.

Все этапы первого уровня определяются заранее. Для каждого этапа фиксируются:

- цель;
- что входит в этап;
- какой результат должен быть получен;
- состояние этапа.

### Уровень 2 — спринт

Спринт — законченная часть текущего этапа первого уровня.

Спринты конкретного этапа определяются непосредственно перед началом этого этапа.

Для каждого спринта должны быть определены:

- что именно разрабатывается;
- зачем это нужно текущему этапу;
- ожидаемый результат;
- критерий завершения.

Предпочтительный принцип:

> Один основной сервис — один спринт.

Завершение первого спринта сервиса не означает production-final реализацию. Спринт должен дать рабочую архитектурную основу и необходимый на текущем этапе интерфейс.

### Уровень 3 — шаг

Шаги определяются непосредственно перед началом конкретного спринта.

Шаг должен быть достаточно локальным и законченным, чтобы не требовать постоянного повторного анализа всего проекта.

---

## Правила изменения плана

Дорожная карта является направляющей, но не неизменяемой.

Допускается:

- добавить шаг, если без него невозможно корректно завершить спринт;
- разделить слишком крупный шаг;
- объединить шаги;
- изменить состав будущих спринтов после получения новой информации;
- изменить порядок будущих этапов при объективной необходимости.

Не следует:

- расширять текущий спринт функциями, которые не нужны для его результата;
- добавлять работу только потому, что «раз уж мы здесь, можно сделать ещё и это»;
- детализировать далёкие этапы раньше времени;
- менять цель текущего спринта без явной необходимости.

---

## Отчёты по спринтам

Для каждого спринта создаётся отдельный файл в `docs/development/sprints/`.

Файл создаётся перед стартом спринта и содержит:

- цель;
- ожидаемый результат;
- критерий завершения;
- согласованные шаги.

После завершения в тот же файл добавляются:

- что фактически реализовано;
- отклонения от плана и причины;
- выполненные проверки;
- известные ограничения;
- итоговый commit SHA.

# Этапы первого уровня

## L1-01 — Ядро платформы

**Статус:** в разработке.

### Цель

Создать самодостаточную универсальную платформу диспетчеризации, которая способна работать с реальным оборудованием и служить основой для последующих плагинов.

### В этап входит

- общая структура backend на C++;
- Data Hub;
- Event Hub;
- Service Hub;
- Device Manager;
- устройства и метрики;
- записываемые метрики;
- state-метрики;
- диспетчер событий / аварий;
- проекты;
- пользователи и права доступа;
- режим управления;
- Package Manager;
- общий Web UI;
- Dashboard;
- мнемосхемы;
- базовая драйверная инфраструктура;
- драйвер Modbus;
- драйвер SNMP;
- необходимые общие библиотеки проекта.

Modbus и SNMP разрабатываются вместе с ядром, чтобы ядро проверялось на реальном взаимодействии с оборудованием.

### Результат этапа

После завершения этапа система должна позволять:

- подключить оборудование через Modbus и SNMP;
- создать или настроить устройства и метрики;
- получать текущие значения через Data Hub;
- хранить актуальные значения и state-метрики;
- записывать значения в управляемые метрики;
- видеть данные в Web UI;
- использовать Dashboard и мнемосхемы;
- формировать и отображать события и аварии;
- разграничивать доступ пользователей;
- работать с проектами;
- устанавливать и управлять пакетами;
- расширять систему без переработки ядра.

## Спринты L1-01

### CORE-001 — Data Hub

**Статус:** завершён.

**Цель:** создать первый самостоятельный backend-сервис и базовый runtime-механизм текущих значений метрик.

**Результат:** Data Hub отдельно собирается и тестируется, принимает и хранит актуальные значения метрик и state-метрик, отдаёт текущее значение, уведомляет подписчиков и поддерживает базовый путь записи через внешний контракт.

План и итоговый отчёт: [`sprints/CORE-001.md`](sprints/CORE-001.md).

### CORE-002 — Service Hub

**Статус:** завершён.

**Цель:** создать адресное взаимодействие и request/response между сервисами.

**Результат:** сервисы обращаются друг к другу через общий системный механизм без прямых C++ зависимостей между внутренними реализациями. Service Hub предоставляет реальную межпроцессную границу, а минимальный клиентский путь пригоден для использования следующим спринтом Web Shell.

План и итоговый отчёт: [`sprints/CORE-002.md`](sprints/CORE-002.md).

### CORE-003 — Web Shell

**Статус:** завершён.

**Цель:** создать базовую Web-оболочку платформы на React + TypeScript.

**Результат:** существует самостоятельное Web-приложение с компактным global Header, глобальной навигацией, рабочей областью, shared React Service Hub connection и проверенной реальной browser-facing Service Hub integration.

План и итоговый отчёт: [`sprints/CORE-003.md`](sprints/CORE-003.md).

### CORE-004 — Project Manager

**Статус:** завершён.

**Цель:** реализовать проекты как самостоятельные точки консолидации и контекста.

**Результат:** проекты можно создавать, получать, изменять и использовать как контекст платформы без превращения их во владельцев остальных ресурсов.

План и итоговый отчёт: [`sprints/CORE-004.md`](sprints/CORE-004.md).

### CORE-005 — Users & Access

**Статус:** планирование.

**Цель:** добавить пользовательский контекст и контроль доступа.

**Результат:** backend и Web выполняют действия в контексте пользователя и проверяют права просмотра, управления, редактирования и администрирования, включая режим управления.

План спринта: [`sprints/CORE-005.md`](sprints/CORE-005.md).

### CORE-006 — Device Manager

**Цель:** создать источник истины об устройствах и описании их метрик.

**Результат:** Device Manager знает устройства, метрики, read/write свойства, state-связи и метаданные, а Data Hub остаётся источником текущих runtime-значений.

### CORE-007 — Package Manager

**Цель:** создать единый механизм управления пакетами до реализации реальных протокольных драйверов.

**Результат:** платформа умеет устанавливать, включать, отключать и удалять пакеты и предоставляет базовый Web-интерфейс Package Manager.

### CORE-008 — Driver Runtime / Driver Manager

**Цель:** создать универсальную инфраструктуру протокольных драйверов.

**Результат:** новый драйвер можно реализовать как самостоятельный компонент, подключающийся к Device Manager, Data Hub и Package Manager без изменения их внутренних реализаций.

### CORE-009 — Modbus Driver

**Цель:** реализовать первый реальный протокольный драйвер.

**Результат:** работает реальный поток чтения `Modbus → Driver → Data Hub` и обратный поток записи до Modbus-оборудования.

### CORE-010 — SNMP Driver

**Цель:** реализовать второй реальный протокол и проверить универсальность Driver Runtime.

**Результат:** SNMP-данные становятся обычными метриками платформы, а драйверная архитектура подтверждает независимость от Modbus.

### CORE-011 — Event Hub

**Цель:** создать отдельное пространство обмена событиями и авариями.

**Результат:** события публикуются и доставляются подписчикам независимо от realtime-потока Data Hub.

### CORE-012 — Event Manager

**Цель:** реализовать формирование событий, аварий и state-метрик на основе реальных данных.

**Результат:** изменение метрики может изменить её state, сформировать событие/аварию и отобразиться в Web через Event Hub.

### CORE-013 — System & Administration

**Цель:** включить саму платформу в общую модель мониторинга и добавить базовое администрирование.

**Результат:** CPU, RAM, диск, uptime и состояния сервисов представлены через общие механизмы метрик и событий, а администратор получает необходимые базовые инструменты.

### CORE-014 — Dashboard

**Цель:** создать рабочую основу универсального конструктора пользовательских страниц.

**Результат:** инженер может создать Dashboard из контейнеров и базовых компонентов, использовать параметры/контекст и отображать реальные метрики и state без написания Web-кода.

### CORE-015 — Mimics

**Цель:** реализовать мнемосхемы как самостоятельный SVG-ресурс внутри Dashboard.

**Результат:** можно создать операторский экран с привязками к реальным метрикам, state, динамическими свойствами и управляемыми значениями.

### CORE-016 — Core Integration & Stabilization

**Цель:** проверить завершённость L1-01 как одной работающей платформы.

Это осознанное исключение из правила «один сервис — один спринт»: новый сервис здесь не создаётся.

**Результат:** ядро можно развернуть из чистого состояния, подключить Modbus/SNMP оборудование, создать пользователя, проект, устройство и метрики, получить значения, выполнить разрешённую запись, увидеть state и событие/аварию, использовать Dashboard и мнемосхему и управлять пакетами.
