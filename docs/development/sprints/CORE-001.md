# CORE-001 — Data Hub

## Статус

**Завершён.**

После успешного Step 9 выполнена обязательная финальная ревизия документации CORE-001.

Этап: `L1-01 — Ядро платформы`.

Этот файл является одновременно планом спринта и итоговым отчётом.

## Цель

Создать первый самостоятельный backend-сервис платформы — Data Hub — и базовый runtime-механизм работы с текущими значениями метрик.

Data Hub должен существовать как отдельный микросервис с собственным внешним контрактом и отдельной сборкой.

## Ожидаемый результат

К завершению спринта должен существовать отдельный C++ Data Hub, который:

- собирается и тестируется в Linux-среде через WSL;
- принимает текущее значение метрики;
- хранит последнее актуальное значение;
- отдаёт текущее значение по запросу;
- позволяет подписываться на изменения;
- при новой подписке сразу отдаёт уже существующее актуальное значение, затем доставляет новые изменения;
- работает со state-метриками;
- имеет базовый внешний путь запроса записи управляемой метрики;
- не содержит исторического архива;
- не содержит бизнес-логики устройств, аварий, проектов или пользователей.

## Критерий завершения

Спринт завершён, если через внешний контракт Data Hub подтверждается сценарий:

1. Publisher публикует значение метрики.
2. Data Hub сохраняет его как текущее.
3. Другой клиент получает текущее значение по запросу.
4. Новый Subscriber подписывается и сразу получает уже существующее значение.
5. Publisher публикует новое значение.
6. Subscriber получает изменение.
7. State-метрика публикуется, хранится и доставляется тем же общим механизмом.
8. Запрос записи управляемой метрики доходит через Data Hub до тестового получателя записи.
9. Data Hub корректно запускается, останавливается и проходит обязательные тесты.

# Шаги

## Step 1 — Каркас Data Hub и сборка

### Что делаем

Создаём минимальную структуру C++ проекта, необходимую для первого реального микросервиса.

На этом шаге:

- создаём отдельный Data Hub executable;
- создаём отдельную цель тестов;
- определяем минимальную структуру исходников;
- выбираем и фиксируем необходимый C++ standard, build system и минимальный инструментарий;
- обеспечиваем сборку в WSL;
- проверяем отдельный запуск сервиса и тестов.

Не создаём отдельный абстрактный спринт «каркас всего проекта»: общая основа появляется как часть первого реального сервиса и затем переиспользуется.

### Результат

В WSL независимо собираются и запускаются Data Hub executable и Data Hub tests. Логика метрик пока не является целью.

## Step 2 — Внешний контракт Data Hub

### Что делаем

Определяем минимальный внешний контракт:

- идентификатор метрики;
- представление значения;
- тип значения;
- необходимые runtime-метаданные;
- публикация значения;
- запрос текущего значения;
- подписка;
- запрос записи значения.

Также выбираем и фиксируем конкретный транспорт и формат взаимодействия, необходимые для практической реализации Data Hub.

Контракт должен быть независим от внутренних C++ классов сервиса и не должен проектироваться «на все будущие случаи».

### Результат

Будущий независимый сервис способен взаимодействовать с Data Hub через формальный внешний контракт.

## Step 3 — Хранилище текущих значений

### Что делаем

Реализуем runtime-хранилище:

`metricId → current value`

Новая публикация заменяет предыдущее актуальное значение той же метрики.

История не хранится.

### Результат

После `Temperature = 22.1`, затем `Temperature = 22.8`, Data Hub возвращает `22.8`. Поведение покрыто тестами.

## Step 4 — Публикация и получение текущего значения

### Что делаем

Подключаем хранилище к внешнему контракту.

Один независимый клиент должен публиковать значение, другой — получать последнее актуальное значение.

### Результат

Работает реальное межпроцессное взаимодействие через границу Data Hub, а не только вызов внутренних C++ классов.

## Step 5 — Подписки

### Что делаем

Реализуем подписку на изменения метрик.

Новый подписчик получает текущее значение, если оно уже существует, а затем дальнейшие изменения.

Пример:

1. `Temperature = 25`.
2. Подключается Subscriber.
3. Он сразу получает `25`.
4. Publisher публикует `26`.
5. Subscriber получает `26`.

### Результат

Работает базовая publish/subscribe модель с retained-подобным получением актуального значения при подписке.

## Step 6 — State-метрики

### Что делаем

Добавляем согласованную модель связанной метрики состояния.

Концептуально:

`AHU01.Temperature`

`AHU01.Temperature.State`

Data Hub хранит и распространяет state-метрику, но не вычисляет `Normal`, `Warning`, `Alarm`, `NoData`, `Maintenance` и другие состояния.

### Результат

Потребитель может получать и подписываться как на рабочую метрику, так и на её актуальную state-метрику.

## Step 7 — Базовый путь записи метрики

### Что делаем

Разделяем:

- публикацию фактического текущего значения источником;
- запрос изменить writable-метрику.

Реального драйвера пока нет, поэтому используем тестового получателя записи.

Проверяем:

`Client → write(metricId, value) → Data Hub → Test metric provider`

Пользовательские права в этом спринте не реализуются.

### Результат

Существует и тестируется обратный путь управления, который позднее будет использован Driver Runtime и драйверами.

## Step 8 — Жизненный цикл и базовая обработка ошибок

### Что делаем

Проверяем необходимый минимум поведения самостоятельного сервиса:

- корректный запуск;
- корректную остановку;
- обработку некорректного запроса;
- поведение при неизвестной метрике там, где это применимо;
- отключение подписчика;
- повторное подключение клиента;
- базовые диагностические сообщения.

Не создаём большую production-систему логирования.

### Результат

Data Hub корректно работает как отдельный процесс не только в happy-path тестах.

## Step 9 — Проверка спринта и итоговый отчёт

### Что делаем

Новых функций не добавляем, кроме исправлений, необходимых для выполнения критериев.

Проверяем цепочку:

1. Publisher публикует `Temperature = 23`.
2. Data Hub хранит `23`.
3. Запрос возвращает `23`.
4. Subscriber подключается и сразу получает `23`.
5. Publisher публикует `24`.
6. Subscriber получает `24`.
7. Публикуется `Temperature.State = Warning`.
8. State доступен и доставляется подписчику.
9. Выполняется `write(Setpoint, 25)`.
10. Тестовый получатель записи получает запрос.

После этого:

- выполняем обязательную сборку;
- запускаем тесты;
- выполняем необходимую интеграционную проверку;
- исправляем проблемы в рамках спринта;
- заполняем итоговый отчёт;
- фиксируем итоговый commit SHA.

### Результат

Все критерии `CORE-001` подтверждены проверками.

# Итоговый отчёт

## Фактически реализовано

- отдельный backend-сервис Data Hub на C++20;
- сборка через CMake 3.20+ и Ninja в Linux/WSL;
- внешний versioned-контракт `dispatcher.data_hub.v1` на gRPC + Protocol Buffers proto3;
- `MetricId` как непрозрачный строковый идентификатор;
- `MetricValue` с `bool`, `int64`, `uint64`, `double`, `string`, `bytes`;
- runtime sample с source timestamp;
- потокобезопасное хранение одного актуального значения на metric ID без истории;
- `PublishMetric` для публикации фактического текущего значения;
- `GetCurrent` для получения последнего опубликованного значения;
- server-streaming `Subscribe` на явно перечисленные metric IDs;
- retained-подобная семантика: существующее актуальное значение сначала, затем live updates;
- state-метрики через тот же универсальный runtime-механизм без специального state store или state RPC;
- `WriteMetric` как отдельный запрос управления, не подменяющий фактическое текущее значение;
- внутренний `WriteRouter` и `MetricWriteProvider` для проверки доставки write request владельцу метрики;
- базовые gRPC status-коды для некорректных и неизвестных запросов;
- повторное подключение клиентов в пределах одного работающего процесса;
- корректная остановка Linux-процесса по SIGINT/SIGTERM;
- bounded graceful shutdown gRPC;
- lifecycle-диагностика без отдельного logging framework.

## Выполненные проверки

Перед фиксацией implementation + acceptance commit Step 9 была выполнена полная WSL-проверка:

- чистая конфигурация CMake;
- сборка `dispatcher_data_hub`;
- сборка regression test target;
- сборка отдельного sprint acceptance target;
- `data-hub.lifecycle-and-errors`;
- `data-hub.sprint-acceptance`;
- `data-hub.signal-term`;
- `data-hub.signal-int`.

Отдельный `data-hub.sprint-acceptance` подтверждает согласованную цепочку спринта:

1. `Temperature = 23`;
2. `GetCurrent(Temperature) = 23`;
3. новый Subscriber сразу получает retained `23`;
4. после публикации `Temperature = 24` Subscriber получает `24`;
5. `Temperature.State = Warning` публикуется обычным metric path;
6. Subscriber получает `Temperature.State = Warning`;
7. `GetCurrent(Temperature.State) = Warning`;
8. `WriteMetric(Setpoint, 25)` доходит до test provider;
9. один `WriteMetric` сам по себе не создаёт ложное factual current value для Setpoint.

Regression-проверки дополнительно покрывают ошибки RPC, отключение/переподключение клиента и завершение активных subscriptions при shutdown.

## Отклонения от плана

Существенного расширения scope не было.

В ходе реализации были сделаны два архитектурных уточнения:

- для state-метрик не потребовался специальный механизм Data Hub: они являются обычными метриками, а связь рабочей метрики со state-метрикой остаётся будущей описательной ответственностью Device Manager;
- базовый write path заканчивается внутренним `MetricWriteProvider`; отдельный межпроцессный протокол регистрации Driver Runtime намеренно не спроектирован раньше спринта Driver Runtime.

В Step 8 при чистой сборке GCC 15 обнаружил most-vexing-parse в создании `DataHubServer`; ошибка была исправлена внутри того же шага до фиксации его commit SHA.

## Известные ограничения

- runtime current values не восстанавливаются после рестарта Data Hub;
- исторические значения не хранятся;
- Data Hub пока не проверяет пользователей, права и control mode;
- Data Hub не владеет writable/read-only и другой описательной metadata метрик;
- финальный enum state-значений не определён;
- реальная регистрация/маршрутизация к отдельному Driver Runtime ещё не существует;
- текущий `MetricWriteProvider` является только внутренним C++ port Data Hub;
- gRPC сейчас использует insecure server/channel credentials, production security не входит в CORE-001;
- очередь каждого Subscriber пока не имеет production backpressure/лимитов;
- quality и время приёма Data Hub пока не входят в `MetricSample`;
- production observability, clustering и HA не реализуются в этом спринте.
