# AGENTS.md — правила работы с Dispatcher

Этот файл обязателен к прочтению любой AI-моделью или агентом перед изменением проекта.

## 1. Главный источник истины

Репозиторий:

```text
https://github.com/Lex26p/dispatcher
```

Рабочая ветка:

```text
master
```

Источник истины — актуальное содержимое репозитория, а не память модели, прошлые ответы или ранее созданные локальные файлы.

Перед каждым шагом:

1. получить текущий HEAD `master`;
2. получить актуальное дерево/список файлов;
3. прочитать `AGENTS.md`;
4. прочитать `README.md`, `docs/ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, если они существуют;
5. прочитать только те дополнительные исходники и конфигурационные файлы, которые реально нужны для текущего изменения;
6. только после этого проектировать изменение и писать файлы.

Если пользователь прислал SHA после предыдущего шага, проверить актуальное состояние репозитория и использовать репозиторий как окончательную базу.

## 2. GitHub используется агентом только для чтения

Агент НЕ должен:

- создавать коммиты;
- push;
- менять файлы через GitHub API;
- создавать/переключать ветки;
- делать merge;
- открывать PR вместо пользователя;
- удалять файлы в репозитории.

Все Git-изменения выполняет пользователь локально.

Работа ведётся в одной ветке `master`, пока пользователь явно не изменит это правило.

## 3. Работа разбивается на шаги

Каждый ответ, который реализует очередной шаг, должен начинаться с:

1. номера текущего шага;
2. ориентировочного количества оставшихся шагов;
3. краткого описания результата текущего шага.

Количество шагов может изменяться. Если задача оказалась слишком большой, лучше разделить её на меньшие проверяемые шаги.

Нельзя начинать следующий функциональный шаг, пока пользователь:

- не подтвердил текущий шаг новым Git SHA; либо
- не прислал ошибку для исправления текущего шага.

Если пришла ошибка, продолжается текущий шаг.

## 4. Перед написанием кода обязательно читать репозиторий

Нельзя генерировать изменения только из предыдущего контекста разговора.

Перед каждым изменением нужно заново получить необходимые файлы из репозитория.

Если фактический код отличается от ожидаемого, следовать фактическому коду.

Не задавать пользователю вопрос о содержимом файла, если его можно получить из репозитория.

## 5. Формат поставки изменений

Агент создаёт ZIP-архив.

ZIP должен содержать:

- только добавленные или изменённые файлы, необходимые текущему шагу;
- каждый файл — целиком, с актуальным содержимым;
- пути относительно корня репозитория.

Пример:

```text
dispatcher-step-03.zip
├── src/
│   └── Dispatcher.Core/
│       └── TagService.cs
└── tests/
    └── Dispatcher.Core.Tests/
        └── TagServiceTests.cs
```

Запрещено вместо исходных файлов класть:

- `.patch`;
- `.diff`;
- скрипт, который генерирует исходники;
- скрипт применения патча;
- Git metadata;
- `bin/`;
- `obj/`;
- временные IDE-файлы.

Архив извлекается поверх локального проекта.

Типовая команда:

```powershell
Expand-Archive -Path "C:\Users\pereverworkki\Downloads\dispatcher-step-XX.zip" -DestinationPath "C:\Projects\dispatcher" -Force
```

Если когда-либо необходимо удалить уже существующий файл, нельзя скрывать удаление внутри скрипта. Нужно явно указать удаляемый путь и отдельную PowerShell-команду. По возможности проектировать шаги так, чтобы удаление не требовалось.

## 6. После архива — команды проверки

После команды распаковки агент обязан дать единый блок команд для проверки текущего шага.

Для .NET-проекта типовая последовательность после появления solution:

```powershell
cd C:\Projects\dispatcher

dotnet restore
dotnet build
dotnet test
```

Если для шага нужен запуск:

```powershell
dotnet run --project .\src\Dispatcher.Server\Dispatcher.Server.csproj
```

Команды должны соответствовать реальной структуре актуального репозитория. Нельзя механически повторять пример, если пути или инструменты изменились.

Если нужен конкретный тест, сначала запускать целевой тест, затем полный набор тестов, когда это целесообразно.

## 7. После команд — ручная проверка

Агент обязан написать конкретный список того, что пользователь должен проверить.

Проверка должна быть наблюдаемой, например:

- ожидаемый результат теста;
- URL;
- HTTP status;
- JSON;
- значение тега;
- изменение регистра;
- состояние Online/Offline;
- конкретное поведение Web UI.

Фраза «проверьте, что всё работает» недостаточна.

## 8. Git-команды всегда выполняет пользователь

В конце успешного шага агент выдаёт команды примерно такого вида:

```powershell
cd C:\Projects\dispatcher

git status
git add .
git commit -m "Осмысленное имя коммита"
git push
git rev-parse HEAD
```

Имя коммита должно соответствовать содержанию шага.

Агент после этого ожидает от пользователя:

- новый SHA; либо
- ошибку/вывод тестов.

Агент не выполняет эти Git-команды сам.

## 9. Дорожная карта обновляется вместе с проектом

Файл:

```text
docs/ROADMAP.md
```

является рабочей дорожной картой.

При развитии проекта:

- завершённые шаги отмечаются `[x]`;
- будущие остаются `[ ]`;
- шаги можно разделять/объединять;
- изменения плана фиксируются в этом файле;
- документация должна изменяться вместе с архитектурой, а не отставать от кода.

Если новое техническое решение меняет архитектуру, обновить:

```text
docs/ARCHITECTURE.md
docs/DECISIONS.md
```

в том же шаге, где меняется реализация.

## 10. Инженерные принципы

### 10.1 Не усложнять преждевременно

Не добавлять без текущей необходимости:

- alarms;
- events;
- historian;
- roles;
- authentication;
- message brokers;
- distributed services;
- generic plugin framework;
- сложные abstractions «на будущее».

### 10.2 Сохранять расширяемые границы

Простота не означает жёсткую связанность.

Ключевая цепочка:

```text
Protocol → logical Tag → Core/TagService → Server → Web
```

Web и мнемосхемы не должны работать напрямую с Modbus-регистрами или SNMP OID.

### 10.3 Изменения должны быть минимальными

На каждом шаге:

- менять только необходимое;
- не делать массовый рефакторинг без причины;
- не обновлять зависимости только ради обновления;
- не форматировать несвязанные файлы;
- не создавать универсальные abstractions без реального второго use case.

### 10.4 Тестируемость

Предпочитать код, который можно проверить без реального оборудования.

Протокольную интеграцию отделять от предметной логики настолько, насколько требуется для unit/integration tests.

При этом не создавать избыточную abstraction hierarchy только ради mock-ов.

### 10.5 Ошибки не скрывать

Не подавлять исключения без причины.

Ошибки связи с устройством должны в будущем превращаться в понятное runtime-состояние, а не исчезать.

## 11. Текущий продуктовый порядок

Главные этапы:

```text
1. Modbus → Web
2. Редактор устройств
3. SNMP
4. Простая мнемосхема
5. Дальнейшее развитие
```

Подробные шаги всегда брать из актуального `docs/ROADMAP.md`.

## 12. Язык и именование

Общение с пользователем и проектная документация — преимущественно на русском языке.

Имена:

- типов;
- методов;
- namespaces;
- проектов;
- переменных;
- API identifiers

используются на английском языке.

Комментарии в коде добавляются только там, где они объясняют неочевидное решение. Код не должен быть заполнен комментариями, повторяющими его синтаксис.

## 13. Приоритет правил

При конфликте:

1. явное последнее указание пользователя;
2. актуальный `AGENTS.md`;
3. актуальные архитектурные документы;
4. актуальный код и тесты;
5. предыдущий разговор.

Если правило пользователя изменилось, соответствующую документацию нужно обновить в ближайшем шаге.
