# Работа над «Диспетчером»

Эта инструкция действует для всего репозитория. Она нужна, чтобы продолжать работу в новом чате без восстановления замысла по старой переписке.

## 1. Задача и роль ассистента

Сейчас создаём **экспериментальное демо с веб-интерфейсом и бэкендом**, чтобы выяснить функциональность, настройки, движение данных и способы работы пользователя. Демо не является основой для обязательного переноса кода на C++ и не должно заранее становиться полноценным продуктом. Архитектуру основной реализации будем проектировать по результатам экспериментов.

Пользователь определяет замысел. Ассистент реализует небольшие проверяемые шаги, критически оценивает предложения и явно обозначает свои допущения. Нельзя незаметно заменять открытый вопрос собственным требованием. Не проектировать всё приложение заранее и не возвращаться к сотням документов.

## 2. Откуда получать контекст

1. Прочитать этот файл.
2. Прочитать [концепцию](docs/concept.md): назначение и согласованный смысл возможностей.
3. Прочитать [карту демо и план](docs/demo.md): текущий шаг, реализованное, имитации, следующие эксперименты.
4. Учесть последние пояснения пользователя и подтверждение текущего шага.
5. Получить из репозитория актуальные исходники, необходимые для задачи.

Репозиторий — источник актуальных сохранённых файлов. Документация направляет к коду, но не заменяет чтение изменяемых файлов. Если документ, код и пояснение пользователя расходятся, явно обозначить расхождение и согласовать смысл, а не придумывать новую концепцию.

Пользователь самостоятельно код не меняет. Скрупулёзное ревью каждого коммита, чтение всей истории и повторное изучение всего проекта не нужны. Достаточно читать нужные актуальные файлы. Если репозиторий недоступен, сообщить об этом; не выдавать старую копию за актуальную.

## 4. Цикл одного шага

Сначала составить предварительную дорожную карту. Далее выполнять по одному небольшому шагу с наблюдаемым результатом. Формат выдачи:

1. Коротко назвать шаг, задачу и цель.
2. Подготовить изменения только для этой задачи, используя актуальные файлы из Git.
3. Выдать ZIP с полными новыми и изменёнными файлами и кратким описанием изменений.
4. Дать готовую команду распаковки из папки загрузок в корень проекта.
5. При необходимости дать команды установки зависимостей, сборки, запуска или тестирования.
6. Коротко написать, что проверить и какой результат ожидается.
7. Дать команды сохранения нужных файлов в Git, коммита, отправки в текущую ветку и получения полного хэша через git rev-parse HEAD.

**Команды пользователю давать обычным текстом, без обратных кавычек и без блоков кода.** Не использовать синтаксис Bash в командах для его Windows. Команды выполнять пользователю; ассистент не имеет доступа к его локальной папке.

Пользователь либо присылает замечания/ошибку, либо после успешной проверки и отправки изменений присылает хэш коммита. Ошибка означает продолжение текущего шага. Хэш означает принятие результата и разрешение перейти к следующему шагу. Не требовать дополнительного подтверждения уже присланного хэша.

При исправлениях учитывать уже выданные файлы текущего шага, которые ещё могли не попасть в Git. Исправленный архив обозначать новой версией и явно объяснять, какую выдачу он исправляет. Если в новом чате этих файлов нет, получить их у пользователя вместо восстановления по догадкам.

Ассистент не коммитит и не отправляет изменения самостоятельно при этом процессе. Не создавать PR, дополнительные ветки и отдельные коммиты документации без необходимости. Не предлагать force push, сбросы или очистку проекта как обычную часть шага.

## 5. Требования к архивам и проверкам

В ZIP находятся готовые файлы с путями относительно корня C:\Projects\dispatcher, без дополнительной внешней папки. Включать только необходимые новые и изменённые файлы. Не выдавать патчи, фрагменты для вставки или скрипты поиска и замены исходников. Это не запрещает обычные исходники и необходимые проекту команды запуска.

Не включать .git, .vs, node_modules, временные результаты, секреты и ненужные файлы. Если требуется удаление или переименование старого файла, отдельно назвать точный путь и дать явную команду: распаковка сама старые файлы не удаляет.

Перед выдачей проверить структуру и читаемость архива. Для кода выполнить доступные и уместные проверки. Указать, что действительно проверено, что имитируется и что нужно проверить пользователю. Не заявлять о запуске на Windows или в Visual Studio, если такого запуска не было.

Для демо можно сознательно упрощать поведение. Не вводить производственные требования к производительности, отказоустойчивости, кластеризации и совместимости, пока они не нужны для рассматриваемого эксперимента. Демо не предлагать для эксплуатации реального объекта как готовую надёжную систему.

## 6. Поддержание документации

- AGENTS.md хранит устойчивые правила взаимодействия, а не дневник.
- docs/concept.md хранит смысл продукта. Новые предложения отличать от подтверждённых пояснений пользователя.
- docs/demo.md хранит фактическую карту реализации, предварительный план и статус текущего шага.

Обновлять затронутые документы вместе с кодом и включать их в тот же архив. Не заводить отдельный файл на каждую страницу, модуль или мелкую правку. Сведения о маршрутах, данных и файлах добавлять по факту реализации; планы не выдавать за существующий код.

При подготовке архива будущий пользовательский хэш ещё неизвестен. Документ может иметь статус «ожидает проверки». Присланный затем хэш снимает это ожидание; статус обновляется в следующем рабочем архиве. Не требовать отдельного коммита только ради записи собственного хэша.

## 7. Анализ и вспомогательные агенты

При необходимости можно привлекать доступных вспомогательных агентов и первичные внешние источники. Главный агент задаёт ограниченный вопрос, проверяет ответы и собирает согласованный вывод. Вспомогательные агенты получают одинаковую концепцию и проверяют гипотезы; границы компонентов тоже являются предметом проверки.

Не назначать устройство центром всей платформы, не превращать проект в владельца оборудования, не вводить живую зависимость от шаблона. Не считать старые списки сервисов утверждённой архитектурой. Не расширять задачу только ради наличия отдельной роли.

Запуск агентов и проверки описывать только тогда, когда они действительно выполнены. Не обещать самостоятельное наблюдение или работу между сообщениями. Если инструменты агентов недоступны, выполнить анализ непосредственно, не имитируя отчёт о независимых запусках.
