# AGENTS.md

# Правила работы над проектом «Диспетчер»

## 1. Назначение этого файла

Этот файл содержит обязательные правила работы AI-агента над репозиторием «Диспетчер».

Его цель — не описать продукт вместо основной документации, а зафиксировать способ разработки и взаимодействия с пользователем так, чтобы в новом чате агент не додумывал рабочий процесс самостоятельно и не менял его без причины.

Перед началом разработки агент должен считать этот файл рабочей инструкцией.

Основные документы проекта:

- `docs/README.md` — карта документации;
- `docs/concept/` — согласованная концепция продукта;
- `docs/architecture/README.md` — согласованная архитектура;
- `docs/development/ROADMAP.md` — дорожная карта;
- `docs/development/sprints/` — планы и отчёты конкретных спринтов;
- `docs/context/CHAT_CONTEXT.md` — дополнительный контекст проекта.

Репозиторий является источником истины.

Переписка используется для обсуждения. После принятия решения оно должно быть отражено в репозитории в подходящем документе или коде.

# 2. Базовый commit и источник истины

## 2.1. Пользователь подтверждает успешный шаг commit SHA

После каждого успешно завершённого шага пользователь отправляет commit SHA.

Этот SHA становится новой базовой точкой для следующей работы.

Агент не должен считать созданный им ZIP или локально подготовленные файлы новой истиной до тех пор, пока пользователь:

1. не распаковал изменения;
2. не выполнил необходимые сборки и проверки;
3. не сделал commit;
4. не отправил новый SHA.

После получения SHA агент должен при необходимости проверить commit в GitHub и использовать его как базу дальнейшей разработки.

## 2.2. Не переходить к следующему шагу без успешного SHA

Если пользователь отправил commit SHA и сообщил, что всё хорошо, можно переходить к следующему шагу.

Если пользователь вместо SHA прислал ошибку сборки, тестов, запуска или поведения программы, текущий шаг считается незавершённым.

В этом случае агент должен:

1. остаться в рамках текущего шага;
2. проанализировать ошибку;
3. получить из репозитория только необходимые для исправления файлы;
4. подготовить исправление;
5. снова выдать ZIP и необходимые команды;
6. дождаться успешной проверки и нового SHA.

Нельзя начинать следующий шаг только потому, что основная часть текущей задачи уже написана.

## 2.3. Содержимое репозитория — единственный источник истины

При определении текущего состояния проекта агент должен опираться на файлы подтверждённого baseline commit в репозитории.

Чат, summary, память модели, ранее подготовленные ZIP-архивы и локальные рабочие каталоги агента могут использоваться только как навигационный контекст: например, чтобы понять, какой файл нужно получить. Они не являются источником актуального содержимого файла или подтверждённого состояния проекта.

Перед изменением существующего файла агент должен получить его текущую версию из репозитория относительно последнего подтверждённого commit SHA.

Нельзя:

- восстанавливать содержимое существующего файла по тексту из чата вместо чтения репозитория;
- считать ранее созданный локальный файл актуальным только потому, что он имеет такое же имя;
- искать локальную копию файла как замену получению его из текущего baseline;
- переносить решение из памяти разговора в код или документацию, если оно не подтверждается текущим репозиторием.

Локальный файл допустимо использовать только как технический кэш после того, как репозиторий текущего baseline подтвердил его точное соответствие, например совпадением Git blob SHA. Источником истины при этом всё равно остаётся репозиторий.

Для нового файла агент также должен сначала получить из репозитория необходимые связанные документы и контракты текущего baseline, а не строить новый файл только по контексту переписки.

# 3. Главное правило: не делать лишнюю работу

Проект со временем станет большим. Бесконтрольное чтение всего репозитория будет тратить время и контекст и может мешать качественной разработке.

Поэтому агент не должен постоянно сканировать весь проект.

## 3.1. Получать минимально достаточный контекст

Перед изменением кода агент сам определяет, какие файлы нужны для текущего шага.

Нужно получить достаточно контекста, чтобы:

- понимать существующую реализацию;
- не придумывать уже существующие интерфейсы заново;
- не сломать ближайшие зависимости;
- корректно собрать и протестировать изменяемую часть.

Но не нужно читать unrelated части проекта «на всякий случай».

### Пример

Если текущий шаг относится к `Data Hub`, обычно могут понадобиться:

- исходники `Data Hub`;
- его публичный интерфейс или контракты;
- общая библиотека сообщений, если она используется;
- build-файлы, относящиеся к этому сервису;
- тесты `Data Hub`;
- файл текущего спринта;
- релевантная часть архитектурной документации.

При этом без причины не нужно читать:

- весь Dashboard;
- все мнемосхемы;
- весь Package Manager;
- будущий плагин истории;
- CCTV;
- СКУД;
- все остальные сервисы.

## 3.2. Расширять область чтения постепенно

Если первоначально выбранных файлов недостаточно, агент должен расширять область анализа по необходимости.

Нормальная последовательность:

1. получить файлы текущего сервиса;
2. получить непосредственно связанные контракты;
3. если обнаружена зависимость — получить её;
4. если изменение затрагивает общий механизм — расширить просмотр до этого механизма;
5. только если задача реально требует общего понимания проекта — просмотреть более широкую часть репозитория.

Полное сканирование репозитория допустимо, если для этого есть объективная причина.

Примеры таких причин:

- крупный рефакторинг общей структуры;
- изменение фундаментального общего контракта;
- начало работы, которая затрагивает много сервисов;
- поиск неизвестной зависимости, которую невозможно локализовать точечным поиском;
- интеграционная проблема, источник которой не удаётся определить локально;
- специальная ревизия всего проекта.

Полное сканирование не должно быть действием по умолчанию перед каждым шагом.

## 3.3. Агент сам выбирает способ получения файлов

Пользователь не должен вручную подсказывать каждый файл.

Агент сам выбирает оптимальный способ:

- точечно получить известный файл;
- посмотреть каталог;
- выполнить поиск по репозиторию;
- получить несколько связанных файлов;
- при необходимости расширить область анализа.

Способ получения файлов должен соответствовать задаче.

Если известны точные файлы, лучше получить их напрямую.

Если неизвестно, где находится реализация, сначала лучше выполнить узкий поиск по имени сервиса, класса, функции, сообщения или ошибки, а не читать весь репозиторий.

# 4. Дорожная карта и уровни планирования

Разработка управляется файлом `docs/development/ROADMAP.md`.

Используются три уровня.

## Уровень 1 — крупный этап продукта

Примеры:

- ядро платформы;
- плагин автоматизации;
- плагин истории.

Темы первого уровня определяются заранее и задают долгосрочное направление продукта. Их изменение является исключением и требует объективной причины, а не удобства текущей реализации.

## Уровень 2 — спринт

Спринт — законченная часть текущего этапа.

Спринты конкретного этапа определяются непосредственно перед началом этого этапа. Агент должен самостоятельно разложить этап на спринты, достаточные для достижения результата этапа, и зафиксировать их в roadmap до начала реализации этапа.

Для текущего `L1-01 — Ядро платформы` спринты уже определены и не должны перепланироваться без объективной необходимости.

Основной предпочтительный принцип:

**один основной сервис — один спринт.**

Это не абсолютное техническое ограничение, но отклонение от него должно иметь причину.

## Уровень 3 — шаг

Перед началом каждого нового спринта агент обязан сначала расписать его на локальные законченные шаги и зафиксировать их в соответствующем файле `docs/development/sprints/`.

План шагов должен быть готов **до начала реализации первого шага** и задавать последовательность, границы и ожидаемый результат спринта, чтобы агент не расширял scope по ходу работы без необходимости.

Если шаги уже зафиксированы в текущем sprint-файле, агент использует их как рабочий план и не придумывает новый план заново.

Шаг должен быть достаточно локальным и законченным, чтобы агенту не приходилось на каждом шаге заново исследовать большую часть репозитория.

# 5. Принцип «один сервис — один спринт»

Платформа разрабатывается не горизонтально «понемногу всего», а преимущественно законченными сервисами.

Нежелательный подход:

1. немного Data Hub;
2. немного Device Manager;
3. немного Event Hub;
4. немного Web;
5. снова Data Hub;
6. снова Device Manager.

Предпочтительный подход:

1. выбрать сервис;
2. определить его текущую ответственность;
3. определить необходимый на этом этапе интерфейс;
4. реализовать рабочую основу сервиса;
5. протестировать её;
6. завершить спринт;
7. перейти к следующему сервису.

## 5.1. Завершённый спринт не означает production-final

Когда первый спринт сервиса завершён, сервис не обязан быть окончательно готов к промышленной эксплуатации на все будущие случаи.

Он должен быть:

- архитектурно осмысленным;
- рабочим в рамках требований текущего этапа;
- тестируемым;
- имеющим понятный интерфейс;
- пригодным для использования следующими компонентами.

В дальнейшем сервис можно расширять отдельными спринтами, когда появятся реальные требования.

Не нужно заранее реализовывать все возможные функции «на будущее».

### Пример

Первый спринт Data Hub может дать рабочий механизм:

- приёма значения;
- хранения текущего значения;
- получения текущего значения;
- подписки на изменения.

Если позже плагину истории или кластеризации потребуется новый механизм, интерфейс Data Hub можно расширить отдельной работой.

Не нужно в первом спринте Data Hub пытаться сразу реализовать все возможные будущие режимы эксплуатации.

---

# 6. Каждый сервис получает интерфейс взаимодействия

При разработке сервиса нужно создавать не только его внутреннюю реализацию, но и понятный способ взаимодействия с ним.

Интерфейс должен покрывать реальные потребности текущего этапа.

Не нужно заранее проектировать огромный API на все будущие случаи.

## Правило

**Сначала минимально достаточный стабильный контракт текущей задачи. Затем расширение по реальной необходимости.**

### Пример

Если Device Manager на текущем этапе должен:

- отдавать устройство по ID;
- отдавать описание метрик устройства;

не нужно автоматически добавлять десятки гипотетических методов, которые пока никем не используются.

Когда следующий сервис реально потребует новый запрос, контракт можно расширить.

---

# 7. Микросервисы создаются сразу

Backend не должен сначала разрабатываться как единый монолит с планом «потом разделить».

Сервисы с самого начала должны иметь физические и логические границы, соответствующие архитектуре проекта.

Причины:

- проект будет большим;
- C++ проект может долго компилироваться;
- пользователь работает на ноутбуке;
- изменение одного сервиса не должно без необходимости пересобирать весь backend;
- прямые зависимости между внутренними C++ классами разных сервисов затруднят дальнейшее разделение;
- Hub и сервисные контракты должны быть реальными границами системы, а не только диаграммой.

## Предпочтительная модель

Каждый крупный backend-сервис должен по возможности иметь:

- собственный исполняемый компонент;
- собственные исходники;
- собственные тесты;
- явно определённые зависимости;
- интерфейс взаимодействия;
- возможность отдельной сборки.

Общие библиотеки допустимы там, где они действительно общие.

Не нужно превращать общую библиотеку в скрытый монолит, куда складывается бизнес-логика всех сервисов.

---

# 8. Сборка должна быть локальной к текущей работе

При изменении одного сервиса по возможности нужно собирать:

- этот сервис;
- его тесты;
- изменённые общие библиотеки;
- необходимые зависимости.

Не нужно каждый раз пересобирать весь проект.

Полная сборка проекта нужна, когда это оправдано, например:

- изменён общий контракт, используемый многими сервисами;
- завершён крупный интеграционный спринт;
- нужно проверить совместимость всей платформы;
- локальная сборка не позволяет проверить изменение.

Это особенно важно, потому что разработка ведётся на ноутбуке и проект будет расти.

# 9. Целевая среда — Linux, локальная разработка — WSL

Основная среда выполнения backend проекта — Linux.

Пользователь работает на Windows, но имеет WSL.

Поэтому backend следует собирать, тестировать и запускать в WSL, если нет отдельной причины выполнять конкретное действие непосредственно в Windows.

Локальный репозиторий пользователя:

`C:\Projects\dispatcher`

Из WSL тот же каталог обычно доступен как:

`/mnt/c/Projects/dispatcher`

## Правило

Не разрабатывать backend как Windows-first приложение с надеждой перенести его на Linux позже.

Linux-совместимость должна проверяться в процессе разработки.

Windows используется как рабочая ОС пользователя и для операций, которым удобнее выполняться из PowerShell, например распаковка ZIP и обычные Git-команды.

WSL используется для Linux-сборки, запуска backend и тестов.

# 10. Полный рабочий цикл одного шага

Каждый шаг разработки проходит по следующей схеме.

## Шаг 1. Кратко описать, что делаем

Перед изменениями агент пишет пользователю короткое описание.

Описание должно отвечать на два вопроса:

1. что будет изменено;
2. что должно получиться после шага.

Не нужно начинать шаг с длинного теоретического текста, если решения уже согласованы.

### Хороший пример

> В этом шаге создаём минимальный каркас Data Hub как отдельного C++ сервиса и отдельную цель его тестов. После шага сервис должен отдельно собираться в WSL и запускаться, но обработку метрик пока не реализуем.

### Плохой пример

> Сейчас немного поработаем над backend и заодно подготовим некоторые вещи на будущее.

Второй вариант не задаёт границу задачи.

---

## Шаг 2. Получить нужные файлы из репозитория

Перед написанием изменения агент получает файлы из текущего базового commit.

Агент сам определяет оптимальный набор.

Он не должен просить пользователя выгружать файлы, которые способен получить из репозитория самостоятельно.

### Пример

Текущий шаг: добавить новую операцию в существующий Device Manager.

Разумный набор чтения:

- публичный контракт Device Manager;
- реализация Device Manager;
- тесты Device Manager;
- его build-файл;
- файл текущего спринта.

Если контракт использует общую библиотеку сообщений — дополнительно получить конкретные файлы этой библиотеки.

Не нужно автоматически читать весь `services/`, весь `web/` и все плагины.

### Если контекста оказалось мало

Допустимо сделать ещё один точечный запрос к репозиторию.

Это лучше, чем заранее читать всё.

---

## Шаг 3. Подготовить ZIP и выдать команду распаковки

Изменения передаются пользователю архивом.

Архив должен быть подготовлен так, чтобы его можно было распаковать непосредственно поверх:

`C:\Projects\dispatcher`

Внутри архива не должно быть лишнего внешнего каталога вроде:

`DISPATCHER_PATCH_001\services\...`

Правильно:

`services\...`

`docs\...`

`tests\...`

то есть пути должны быть относительно корня репозитория.

## В ZIP находятся только готовые файлы проекта

Архив должен содержать итоговые версии файлов, которые после распаковки становятся файлами репозитория:

- исходный код;
- заголовочные файлы;
- тесты;
- конфигурацию и build-файлы;
- документацию;
- другие реальные файлы проекта, необходимые текущему шагу.

Нельзя вместо готовых файлов класть в ZIP:

- patch-файлы;
- diff-файлы;
- временные скрипты, которые после распаковки переписывают файлы проекта;
- генераторы изменений;
- служебные файлы агента, которые не должны оставаться в репозитории.

Агент может использовать скрипты, Python или другие инструменты **в своей рабочей среде** для подготовки архива. Но пользователь должен получить уже готовый overlay, а не механизм, который затем меняет проект на его машине.

Скрипт допустимо включать в ZIP только тогда, когда сам этот скрипт является согласованным постоянным файлом проекта и нужен проекту как часть результата шага. Нельзя включать скрипт только ради применения изменений к другим файлам.

Пример команды распаковки:

    Expand-Archive -Path "C:\Users\pereverworkki\Downloads\DISPATCHER_EXAMPLE_001.zip" -DestinationPath "C:\Projects\dispatcher" -Force

Если изменение требует удалить или переименовать старый файл, одного ZIP может быть недостаточно, потому что распаковка не удаляет существующие файлы.

В таком случае после распаковки нужно явно дать необходимую команду удаления или перемещения.

Нельзя молча оставлять старые файлы, которые должны исчезнуть.

## Шаг 4. При необходимости выдать команды сборки и тестов

Если шаг изменяет исполняемый код, build system, тесты или конфигурацию, обычно нужно дать команды проверки.

Команды должны быть одним цельным блоком и выполняться в логичном порядке.

Для backend основная среда — WSL.

Команды должны соответствовать реально существующему build system проекта. Нельзя выдумывать CMake, Ninja, Meson или другой инструмент, пока он не выбран и не присутствует в репозитории.

Общий пример формы команды:

    wsl bash -lc "cd /mnt/c/Projects/dispatcher && <команда сборки текущего сервиса> && <команда тестов текущего сервиса>"

Это только пример формы. Вместо placeholder должны использоваться реальные команды проекта.

## Запрещено использовать PowerShell continuation через обратную кавычку

Не выдавать PowerShell-команды, разбитые переносами с символом обратной кавычки.

Если команда длинная:

- дать её одной строкой;
- либо разделить на несколько самостоятельных команд.

# 11. Что проверять после сборки

Если автоматических тестов достаточно, не нужно придумывать лишнюю ручную проверку.

Если результат шага требует проверки поведения, агент должен коротко написать, что проверить.

### Пример

После шага Data Hub:

1. запустить сервис;
2. убедиться, что он стартует без ошибки;
3. выполнить тестовый запрос;
4. проверить ожидаемый ответ;
5. остановить сервис.

Для Web шага это может быть:

1. открыть страницу;
2. проверить конкретный компонент;
3. выполнить конкретное действие;
4. убедиться в ожидаемом результате.

Фраза «проверь, что всё работает» недостаточно конкретна.

# 12. Git-команды выдаются после проверки

Git-команды должны идти после сборки, тестов и необходимой ручной проверки.

Нормальный цикл:

изменения → сборка → тесты → ручная проверка при необходимости → commit → push → SHA.

Не нужно просить пользователя коммитить заведомо неработающий шаг.

Типовой блок:

    Set-Location C:\Projects\dispatcher
    git add .
    git status --short
    git commit -m "Краткое описание изменения"
    git push
    git rev-parse HEAD

Commit message должен соответствовать реальному содержанию шага.

## Не использовать `git diff`

В пользовательском workflow не используются команды `git diff`, включая варианты вроде:

- `git diff`;
- `git diff --check`;
- `git diff --stat`;
- `git diff -- <path>`.

Для обычной проверки состава изменений достаточно согласованных сборок/тестов, необходимых ручных проверок и `git status --short`.

Если перед commit необходимы дополнительные Git-команды, они должны быть включены в тот же понятный блок и не должны использовать `git diff`.

# 13. Ответ пользователя после шага

После команд Git агент ждёт один из двух результатов.

## Вариант A — успех

Пользователь отправляет SHA, например:

`0123456789abcdef0123456789abcdef01234567`

Это означает:

- распаковка прошла;
- обязательные проверки прошли;
- изменение принято;
- commit отправлен в репозиторий.

Агент проверяет SHA при необходимости, принимает его как новую базовую точку и может переходить к следующему шагу.

## Вариант B — ошибка

Пользователь отправляет:

- вывод компилятора;
- упавший тест;
- runtime error;
- лог;
- описание неправильного поведения.

Пример:

> Сборка упала: `MetricStore.cpp:42: ...`

В этом случае:

- не выдавать Git-команды для нерабочей версии, если пользователь ещё не коммитил её;
- не переходить к следующему шагу;
- не менять тему спринта;
- сначала исправить ошибку текущего шага.

Если для диагностики нужен дополнительный файл, получить именно его или ближайшие зависимости, а не автоматически сканировать весь проект.

# 15. Изменения плана во время работы

План нужен, чтобы агент не уходил в сторону, но он не должен запрещать необходимые технические корректировки.

Во время спринта можно:

- добавить необходимый шаг;
- разделить слишком большой шаг;
- объединить два очевидно связанных шага;
- изменить порядок шагов, если выявилась зависимость.

Это допускается только тогда, когда изменение реально помогает завершить согласованный результат спринта.

Изменение самого `docs/development/ROADMAP.md`, состава этапов или уже согласованных спринтов является более сильным действием и должно быть исключением. Сначала следует попытаться решить новую техническую необходимость корректировкой шагов текущего спринта. Roadmap меняется только если обнаружено, что ранее зафиксированное направление объективно не позволяет корректно достичь результата продукта или этапа. Причина такого изменения должна быть явно отражена в документации.

## Нежелательный пример

Текущий спринт — Data Hub.

Агент замечает, что в будущем понадобится красивый Dashboard-компонент, и начинает делать его «заодно».

Так делать нельзя.

## Допустимый пример

При реализации подписки Data Hub выясняется, что невозможно корректно продолжить без выделения общего контракта идентификатора метрики.

Можно добавить отдельный шаг создания этого контракта, если он действительно необходим текущему спринту.

Если найденная задача не нужна для текущего результата, её следует отложить.

# 16. Отчёт спринта и документация по ходу работы

Для каждого спринта используется отдельный файл в:

`docs/development/sprints/`

Файл создаётся перед стартом спринта.

В начале он содержит:

- цель;
- ожидаемый результат;
- критерий завершения;
- шаги.

По мере работы sprint-файл является живым рабочим документом. После завершения шага в нём нужно фиксировать реально принятое решение, фактическую реализацию и подтверждённый commit SHA там, где это необходимо для продолжения следующих шагов.

После завершения спринта он дополняется:

- фактически реализованным результатом;
- выполненными проверками;
- обоснованными отклонениями от плана;
- известными ограничениями;
- итоговым подтверждённым baseline спринта.

## 16.1. Документация обновляется на каждом шаге, когда это необходимо

Финальный documentation audit не означает, что в течение спринта агент пишет только код, а затем пытается восстановить принятые решения по переписке.

На каждом шаге агент обязан определить, изменяет ли результат шага уже документированные факты. Если изменяет, соответствующая документация обновляется **в том же шаге** и входит в тот же ZIP вместе с кодом/контрактами.

В частности, по ходу шага следует сразу фиксировать, когда это применимо:

- выбранную технологию и причины выбора;
- новый или изменённый внешний контракт;
- фактическую архитектурную границу;
- статус и результат шага в sprint-файле;
- новые команды сборки, запуска или проверки;
- известное ограничение, важное для следующего шага;
- изменение текущей точки разработки;
- другое решение, которое следующему чату нельзя безопасно восстанавливать только из переписки.

Не нужно механически редактировать все документы после каждого шага. Обновляется только документация, реально затронутая результатом шага.

Согласованное решение не следует откладывать до конца спринта только потому, что позже всё равно будет финальный audit. Репозиторий должен оставаться достаточным источником контекста между шагами и между чатами.

## 16.2. Обязательная проверка актуальности документации в конце спринта

Перед тем как считать спринт завершённым, агент обязан провести целевую ревизию документации, которую мог изменить результат этого спринта.

Финальный audit является проверкой целостности уже ведущейся документации: он должен найти пропущенную рассинхронизацию между файлами, а не впервые восстанавливать историю спринта.

Цель ревизии — не допустить ситуации, когда код и архитектурные решения уже изменились, а основные документы продолжают описывать старое состояние проекта.

В зависимости от содержания спринта нужно проверить релевантные документы, например:

- корневой `README.md` и описание текущего состояния проекта;
- `docs/README.md`, если появились новые важные документы или разделы;
- `docs/architecture/` и документы контрактов, если были приняты или реализованы архитектурные решения;
- `docs/development/ROADMAP.md`, включая статусы и текущую точку разработки;
- файл текущего спринта в `docs/development/sprints/`;
- README изменённого сервиса, модуля или плагина;
- `docs/context/CHAT_CONTEXT.md`, если он содержит факты о текущем состоянии, выбранных технологиях или следующем шаге;
- инструкции сборки, запуска и тестирования, если они изменились.

Это не означает обязательное полное чтение всей документации после каждого спринта. Область проверки выбирается по реальному влиянию завершённой работы и расширяется только при необходимости.

Если ревизия обнаружила устаревшие утверждения, ссылки, статусы, команды или список ещё не принятых решений, они должны быть исправлены до перехода к следующему спринту.

Если изменения документации не нужны, факт проверки всё равно следует кратко зафиксировать в итоговом отчёте спринта.

Спринт не считается окончательно закрытым, пока:

1. выполнены его функциональные критерии;
2. пройдены обязательные проверки;
3. заполнен итоговый отчёт;
4. проверена и при необходимости синхронизирована релевантная документация;
5. пользователь прислал SHA финального commit, а агент проверил его в репозитории.

Если финальный commit одновременно содержит сам итоговый отчёт, не нужно создавать рекурсивные commits только ради записи SHA этого же commit внутрь него. В отчёте можно зафиксировать последний подтверждённый implementation SHA и указать, что финальным baseline является проверенный documentation-closure commit. Его SHA подтверждается пользователем и проверяется перед началом следующего спринта.

Не создавать второй отдельный отчёт, если тот же файл спринта может содержать и план, и итог.

# 17. Изменение общих контрактов

Общий контракт может затронуть несколько сервисов, поэтому здесь правило локальной работы применяется особенно внимательно.

Перед изменением общего контракта нужно определить его реальных потребителей.

Не следует автоматически читать весь проект.

Сначала использовать поиск по:

- имени типа;
- имени сообщения;
- namespace;
- include;
- endpoint;
- topic;
- другому точному идентификатору.

После этого получить конкретных потребителей.

Если контракт действительно используется по всему проекту, более широкая проверка оправдана.

После изменения общего контракта может потребоваться более широкая сборка, чем при локальном изменении одного сервиса.

# 18. Общие библиотеки C++

Для C++ разрешено:

- использовать качественные готовые библиотеки;
- создавать собственные библиотеки проекта.

Собственная библиотека должна появляться тогда, когда существует реально общий код или контракт.

Не нужно создавать абстрактную библиотеку заранее только потому, что «возможно, когда-нибудь это будет переиспользоваться».

Общие библиотеки должны помогать независимости сервисов, а не создавать скрытую сильную связанность между ними.

# 19. Не смешивать архитектурные роли

При разработке нужно соблюдать согласованные границы.

В частности:

- Data Hub работает с текущими значениями метрик и state-метриками;
- Event Hub работает с событиями и авариями;
- Service Hub используется для адресного взаимодействия и request/response;
- Device Manager является источником информации об устройствах и описании их метрик;
- realtime-значения находятся в Data Hub;
- отдельной универсальной сущности Command в ядре нет;
- управление выполняется записью в метрики, для которых разрешена запись;
- state рабочей метрики записывает диспетчер событий/аварий согласно настроенным условиям.

Нельзя в ходе реализации незаметно объединять эти роли только потому, что так быстрее написать текущий код.

Если архитектурное решение оказывается неудобным, сначала нужно обсудить изменение архитектуры, а не молча обойти её в коде.

- по возможности собирать только изменяемый сервис и необходимые зависимости;
- использовать WSL для Linux backend;
- передавать изменения ZIP-архивом с готовыми файлами проекта для распаковки поверх репозитория;
- давать конкретные команды сборки и тестов, если они нужны;
- давать конкретную ручную проверку, если она нужна;
- не использовать `git diff` в выдаваемых пользователю Git-командах;
- выдавать Git-команды после успешных проверок;
- ждать SHA или ошибку;
- после ошибки исправлять текущий шаг;
- после SHA использовать новый commit как следующую базу;
- в каждом шаге обновлять затронутую документацию, если результат шага изменил документированные факты или принятые решения;
- поддерживать sprint report как живой рабочий документ, а не заполнять историю спринта только в конце;
- в конце каждого спринта проводить целевую проверку актуальности документации;
- обновлять sprint report и документацию, когда это требуется согласованным процессом.

# 23. Главный критерий выбора действия

Если агент сомневается между двумя вариантами работы, предпочтение следует отдавать варианту, который:

1. лучше соответствует текущему спринту и шагу;
2. требует меньше лишней работы;
3. сохраняет архитектурные границы;
4. создаёт проверяемый результат;
5. не усложняет проект без текущей необходимости;
6. позволяет следующему шагу опираться на уже готовый интерфейс;
7. не заставляет пользователя выполнять ручную работу, которую агент может сделать сам.

Главная цель процесса:

**двигаться по заранее определённому пути небольшими проверяемыми шагами, сохраняя репозиторий в рабочем состоянии и не раздувая область задачи без необходимости.**
